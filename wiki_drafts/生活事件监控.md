# 生活事件监控

生活事件监控是 Fast Strm 的实时同步能力：每 10 秒轮询 115 网盘生活事件，自动同步本地 STRM，无需等待定时全量扫描。

## 架构示意

```
┌──────────┐     ┌──────────────────┐     ┌──────────────┐
│ 115 网盘  │────▶│  FastStrm 处理引擎  │────▶│  本地 STRM   │
│ 变动事件  │     │ 轮询→分类→映射→处理  │     │  + 媒体服务器  │
└──────────┘     └──────────────────┘     └──────────────┘
```

**核心流程**：115 网盘产生变动事件 → 每 10 秒轮询拉取 → 事件分类 + 路径映射 → 生成/删除 STRM → 触发 Emby 刷新

---

## 启用监控

1. 进入「设置」→「生活监控」
2. 勾选「启用监控」
3. 选择要监控的 115 账号
4. 配置路径映射
5. 保存后会自动开始首次拉取

### 服务重启后自动启动

从 v0.8.2 起，监控支持「懒加载自动启动」：

- 服务重启后，**首次有用户访问监控相关页面或接口时**，系统会自动检查：
  1. 监控配置中「启用监控」是否打开
  2. 监控账号列表是否非空
  3. 每个账号的 Cookie / 凭据是否存在（115：cookie 非空；openlist：url/account/password 齐全）
- 三项条件同时满足，会自动调用 `startMonitor()` 拉起监控，**无需再手动点击「全部启动」**
- 真正的 Cookie 有效性由首次轮询（`oncePoll`）自动检测，若失效会把该账号状态置为 `error`，不会阻塞或死循环
- 每进程仅执行一次（通过 `globalThis.__lifeMonitorsAutoStarted` 保护），HMR 热重载后仍然稳定

## 路径映射

监控通过路径映射确定「网盘路径变动 → 哪个本地 STRM 目录受影响」：

```json
[
  {
    "account": "我的115",
    "cloudPath": "/电影",
    "localPath": "/app/data/strm/电影"
  },
  {
    "account": "我的115",
    "cloudPath": "/电视剧",
    "localPath": "/app/data/strm/电视剧"
  }
]
```

- 只有映射的 `cloudPath` 下的变动才会被处理
- 网盘根目录变动（不在映射内）会被忽略

## 四类事件处理

### 事件类型路由

v1.0.0 起，事件类型严格按参考项目 p115strmhelper 路由：

| 事件类型 | type 值 | 路由到 |
|---------|---------|--------|
| 创建（含回收站还原） | 1, 2, 14, 18, 23 | handleCreateEvent |
| 移动 | 5, 6 | handleMoveRenameQuadrant（四象限） |
| 重命名 | 20, 24 | handleMoveRenameQuadrant（四象限） |
| 删除 | 22 | handleRemoveEvent |
| 新文件夹 | 17 | handleCreateEvent（仅写 DB，不生成 STRM） |

### 创建事件（create）

**场景**：115 网盘新增文件/文件夹（上传、转存、离线下载完成、回收站还原）

**处理流程**：
1. 解析文件路径（通过 cid 反查）
2. type=17（新文件夹）→ 仅写入 DB，不生成 STRM（空文件夹无需 STRM）
3. 在路径映射范围内 → 生成 STRM
4. 文件夹事件 → 递归生成所有子文件 STRM
5. 写入 filePathDb
6. 触发 Emby 刷新（防抖 10 秒）

> 💡 **回收站还原**：115 生活事件将还原归类为"新路径事件"（type=1 或 2），走与新增相同的 create 路径——只要新路径命中 `monitor_life_paths` 媒体目录，就生成 STRM。

### 删除事件（remove）

**场景**：115 网盘删除文件/文件夹

**处理流程**：
1. **熔断检查**：单次轮询删除数 >100 或占比 >50% → 跳过并告警
2. 通过 fileId 在 DB 反查本地 STRM 路径（DB 是唯一真相源）
3. 物理删除 STRM 文件（硬删除，直接 os.Remove，不留 .bak 备份）
4. 删除关联资源（.nfo/.jpg/.srt 等，默认关闭，需配置 RemoveRelatedFiles 开关）
5. 删除 DB 记录
6. 清理空目录（保护映射根目录，需配置 RemoveEmptyDirs 开关）
7. 触发 Emby 刷新

> ⚠️ **熔断保护**：防止 115 API 返回异常导致大规模误删。误触发后可在 115 网盘恢复文件后重新全量扫描生成。

### 重命名事件（rename）

**场景**：115 网盘重命名文件/文件夹

**处理流程**：

v1.0.0 起走四象限决策矩阵，详见下方「四象限决策矩阵」章节。重命名事件（type=20/24）与移动事件共享同一套四象限路由。

### 移动事件（move）

**场景**：115 网盘移动文件/文件夹

**处理流程**：

v1.0.0 起走四象限决策矩阵，详见下方「四象限决策矩阵」章节。

## 四象限决策矩阵（v1.0.0 新增）

参考 p115strmhelper 实现，根据「旧路径是否在媒体映射」和「新路径是否在媒体映射」两个维度，将 move/rename 事件路由到 4 个象限：

| 象限 | oldIsMedia | newIsMedia | 场景举例 | 处理策略 |
|------|-----------|-----------|---------|---------|
| OTHER_TO_MEDIA | ❌ | ✅ | 文件从根目录重命名/移动到「电影」目录 | 清理旧 STRM + 在新位置创建 |
| MEDIA_TO_MEDIA | ✅ | ✅ | 文件从「电影/科幻」移动到「电影/动作」 | move/rename（local_move 原子搬移 或 recreate 删旧+生新） |
| MEDIA_TO_OTHER | ✅ | ❌ | 文件从「电影」移出到「备份」 | 删除旧 STRM + 空目录清理 |
| OTHER_TO_OTHER | ❌ | ❌ | 文件在非媒体目录间重命名/移动 | 按文件名兜底搜索（可选） |

### 各象限详细处理

#### 1. OTHER_TO_MEDIA

1. `cleanupOldStrmForOtherToMedia` → 按 file_id 反查 DB 旧路径，找到则删除旧 STRM
2. `handleCreateEvent` → 在新位置创建 STRM

> 这是重命名/移动后旧 STRM 没被删除的 bug 修复关键——v1.0.0 新增了第 1 步清理。

#### 2. MEDIA_TO_MEDIA

按 `moveMediaMode` 配置分两种处理：

- **local_move 模式**（默认）：`os.Rename` 原子搬移（旧文件物理消失到新位置 = 删旧+生新）。失败直接返回错误，不降级。
- **recreate 模式**：先 `cleanupOldStrmAssets` 删旧 STRM + 关联文件 + DB 记录，再在新位置创建新 STRM。强制创建，不被 `moveMediaCreateNewStrm` 挡住。

#### 3. MEDIA_TO_OTHER

1. 反查 DB 旧路径
2. `MoveOutRemoveLocalStrm=true`（默认）→ 删除旧 STRM + 关联文件 + 空目录清理 + DB 删除
3. `MoveOutRemoveLocalStrm=false` → 保留旧 STRM，仅记录日志

#### 4. OTHER_TO_OTHER

1. `MoveOutRemoveLocalStrm=true` → 按文件名在映射目录查找 → 找到则删旧 STRM
2. 没找到 → 跳过（不处理非媒体目录操作）

### 关键设计原则

- **DB 是唯一真相源**：所有路径反查通过 `resolveOldCloudPathByFileID`，不扫描本地文件
- **rename/move 失败即终止**：与参考项目 `shutil_move` 抛异常行为一致，不再降级 fallback
- **关联文件原子迁移**：`.nfo/.jpg/.srt/.ass/.sub` 通过 `moveOrRenameRelatedAssets` 跟随主文件处理
- **DB 路径前缀批量更新**：文件夹移动/重命名后调用 `UpdatePathPrefixBatch` + `UpdateFolderPathPrefixBatch`

## 首次拉取模式

`firstPullMode` 控制首次启用监控时如何处理历史事件：

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `latest` | 只拉取最新一批事件 | 默认，避免重复生成 |
| `all` | 拉取所有历史事件 | 需要补齐遗漏 |
| `last` | 从上次断点继续 | 重启后恢复 |

---

## 断点恢复

`lifeMonitorState.json` 记录每个账号的最后处理时间戳：
- 容器重启后从断点继续，不会遗漏事件
- 如果断点超过 7 天（115 历史保留期），自动切换到 `latest` 模式

---

## 与全量扫描的互斥

全量扫描任务执行时会自动暂停监控，避免 API 和 DB 竞争：

1. 全量扫描开始 → `suspendMonitorForFullScan(account)`
2. 全量扫描结束/异常 → `clearMonitorSuspend(account)`（finally 保证）
3. 监控超时恢复：10 分钟（`FULLSCAN_TIMEOUT_MS`）

---

## API 降级

115 生活事件 API 有两个端点：
- **iOS API**（`/ios/...`）：返回结构更完整，但偶发 405
- **Web API**（`/web/...`）：稳定，但某些字段缺失

监控自动降级：iOS 405 → 切 Web API，用户无感。

---

## 移动/重命名模式

`moveMediaMode` 控制移动事件的处理方式：

| 模式 | 行为 |
|------|------|
| `recreate`（默认） | 删旧 STRM + 在新位置重新生成 |
| `local_move` | 本地移动 STRM 文件（更快，但路径映射必须精确） |

## v1.0.2 更新

### 关键 Bug 修复

- **STRM 生成失效修复**：v1.0.1 及之前版本默认调用 webapi.115.com/behavior/detail，该端点返回的 pick_code 字段经常缺失，导致单文件创建事件被全部跳过。v1.0.2 改为默认走 proapi.115.com/ios/behavior/detail（字段完整），失败时回退 webapi。

- **硬删除默认开启**：EnableHardDelete 默认改为 	rue，删除 STRM 时直接 os.Remove，不再生成 .deleted.bak 备份。所有路径（监控事件 + auto_clean 对账清理）统一硬删除。

### 新增功能

- **错误主动 TG 通知**：监控出错不再静默。Cookie 失效、轮询异常、批量事件处理失败时主动推送 TG 通知。

- **仅错误通知模式**：LifeMonitor 设置页新增「仅错误时发 TG 通知」复选框。开启后正常操作不推送，仅错误时推送，避免高频刷屏。

### Emby webhook 诊断

Emby webhook 入口新增诊断日志，方便排查入库/播放通知是否生效。查看 pp.log 中 [emby/webhook] 关键字确认 webhook 是否真的收到。
