## 1. P0-1 限流分层

### 1.1 现状确认

```go
// internal/service/client115/files.go:89-96
func (c *Client) acquireAPI(ctx context.Context) error {
	lim := rate.GetRegistry().GetLimiter("global", rate.TypeAPI115)
	return lim.Acquire(ctx)
}
```

已核实的事实：

- key 硬编码 `"global"`，**全进程唯一桶**
- 默认 60 QPM，`burst = 60`（`rate/limiter.go:28`，`maxTokens` 初始化为整分钟量）
- `Registry.SetDefaults` 生产代码零调用（已 grep 全仓，只有 `rate_integration_test.go`）
- `GetDownloadUrlWebFull` → `request115`（`files.go:254`）→ `acquireAPI`，**与扫描共用同一桶**

### 1.2 关键设计决策：不改 10+ 个调用点

最直觉的做法是给 `FsFiles`/`GetDownloadUrlWebFull` 都加 `account` 参数，但 `FsFiles` 有 10+ 调用点，改动面大且易漏。

**改用 cookie 派生账号维度**——115 cookie 必含 `UID`（`cookie.go:17-54` 的 `ValidateCookie` 已强制要求 `UID/CID/SEID/KID`）：

```go
// internal/service/rate/key.go（新增）
// AccountKeyFromCookie 从 115 cookie 解析 UID 作为限流维度。
// 解析失败回落 "global"，保证行为可预测（不会因为 cookie 畸形而完全不限流）。
func AccountKeyFromCookie(cookie string) string {
	for _, part := range strings.Split(cookie, ";") {
		part = strings.TrimSpace(part)
		if strings.HasPrefix(part, "UID=") {
			if v := strings.TrimSpace(strings.TrimPrefix(part, "UID=")); v != "" {
				return "uid:" + v
			}
		}
	}
	return "global"
}
```

这样**所有调用点的签名都不用动**，只在 `request115` 内部取 `opt.Cookie` 派生 key。

### 1.3 限流类型与默认值

```go
// rate/registry.go:10-14
const (
	TypeAPI115   LimiterType = "api115"   // 扫描/目录/元数据：60 QPM/账号，burst 15
	TypePlayback LimiterType = "playback" // 播放取直链：120 QPM/账号，burst 30  ← 新增
	TypeLife     LimiterType = "life"     // 生活事件：60 QPM/账号，burst 15     ← 新增
	TypeDownload LimiterType = "download" // 元数据下载
	TypeProxy    LimiterType = "proxy"    // 代理并发（走 Bottleneck）
)
```

burst 必须显式小于 QPM，否则一个突发就能吃掉整分钟配额：

```go
// rate/limiter.go 新增构造函数（保留原 NewLimiter 行为不变）
func NewLimiterBurst(maxTokensPerMinute, burst int) *Limiter {
	if maxTokensPerMinute <= 0 { maxTokensPerMinute = 60 }
	if burst <= 0 || burst > maxTokensPerMinute { burst = maxTokensPerMinute }
	return &Limiter{
		tokens:         float64(burst),
		maxTokens:      float64(burst),
		refillRate:     float64(maxTokensPerMinute) / 60.0,
		lastRefillTime: time.Now(),
	}
}
```

### 1.4 全局兜底上限

多账号同时播放 + 扫描，总 QPS 可能触发 115 风控。加一层全局兜底：

```go
// rate/registry.go
func (r *Registry) Acquire(ctx context.Context, accountKey string, t LimiterType) error {
	// 先过全局兜底（burst 小，只防雪崩，不参与日常调度）
	if err := r.globalCap().Acquire(ctx); err != nil {
		return err
	}
	return r.GetLimiter(accountKey, t).Acquire(ctx)
}
```

> ⚠️ 顺序很重要：全局桶在前会让扫描把播放挡在门口。但因为扫描自身被 60 QPM/账号限制，且全局 300 QPM，正常情况下全局桶始终有令牌，**实际不会造成饿死**。这个设计依赖"扫描桶足够小"，务必保持 `api115QPM * 账号数 < globalCapQPM`。

## 2. P0-4 STRM 前缀校验

### 2.1 现状

```go
// config/config.go:132
Host: getEnv("SERVER_HOST", "0.0.0.0"),
```
```go
// server/server.go:111
baseURL := fmt.Sprintf("http://%s:%d", cfg.Server.Host, cfg.Server.Port)
```

`StrmPrefix` 默认空 → `resolveStrmSettings`（`executor_utils.go:55-68`）兜底到 `baseURL` → **写入 `http://0.0.0.0:8090/api/strm`**。

监控侧兜底是 `127.0.0.1:8090`（`wire.go`），与任务侧不一致。

### 2.2 方案

新增校验函数 + 分级兜底链：

```go
// internal/service/strm/prefix.go（新增）
// IsUnusablePrefix 判断前缀是否不可用于跨机播放：
// 0.0.0.0 / :: / 127.0.0.1 / localhost 都视为不可用（同机播放除外）。
func IsUnusablePrefix(raw string) bool

// DetectLANIP 返回本机首个非回环 IPv4；无网卡时返回 ""。
func DetectLANIP() string
```

`resolveStrmSettings` 兜底链改为：

```
任务级 prefix
 → 全局 settings.strmPrefix
 → 请求上下文 Host（自动学习，见 2.3）
 → 网卡内网 IP
 → 报错（不再静默写 0.0.0.0）
```

### 2.3 自动学习（不静默写入）

**不采用**"静默把访问 Host 写进配置"——反代/内网穿透场景下会写错。

改为：
1. 管理员从非回环地址访问 Web UI 时，`GET /api/settings/prefixHint` 返回 `{"detected":"http://192.168.1.10:8090"}`
2. 前端在 STRM 前缀输入框旁显示"检测到当前访问地址，一键填入"
3. 用户确认后写入

### 2.4 扫描前硬校验

```go
// task/executor.go 扫描开始前
if strm.IsUnusablePrefix(resolved.StrmPrefix) {
    msg := "STRM 前缀为回环/0.0.0.0 地址，生成的文件无法被其他设备播放，请在设置中填写局域网或公网地址"
    // 任务直接失败并给出可操作提示，不生成任何文件
}
```

**这是行为变更**：以前"能跑但播不了"，现在"直接报错"。需要在 CHANGELOG 里明确写。

### 3.4 老配置迁移

存量用户 `settings.json` 里是 `maxThreshold: 10`。直接改默认值会让他们"突然能删 1000 个"，风险太大。

**迁移规则**（在 `config.Load` 后执行一次，幂等）：

```
if MaxRatio == 0 && MaxThreshold == 10 {   // 未升级过
    MaxRatio = 0.10
    MaxThreshold = 1000
}
```

即：**只有确认是老默认值才升级**，用户自己调过的（比如 50）保持不动。

### 3.5 Protected 语义（学 LitePan）

触发保护态时：

- ✅ 生成 / 更新 STRM 照常
- ❌ 所有删除动作停止
- 📢 结果标记 `Protected`，原因写入任务历史 + 通知（Telegram/Webhook）
- 🔧 用户可在清理页手动确认后放行

关键区别：**不是任务失败**。以前是"任务成功但什么都没删"，用户完全不知道；现在是"任务成功、明确告诉你为什么没删"。

## 4. P0-2 STRM URL 签名

### 4.1 设计要点：只签 account + pickcode

**这是整个方案最容易踩坑的地方。** EmbyProxy 在 `resolveRedirectChain` 里会往 query 追加 `redirect=1`：

```go
// embyproxy/proxy.go:1329-1343
headURL := startURL
if isSelfStrmEndpoint(startURL) {
	u, _ := url.Parse(startURL)
	q := u.Query()
	q.Set("redirect", "1")
	u.RawQuery = q.Encode()
	headURL = u.String()
}
```

如果签名覆盖整个 query，这次追加会直接让签名失效，导致反代播放全挂。

因此：

```
sig = base64url( HMAC-SHA256(secret, account + "\x00" + pickcode) )[:22]
```

**只覆盖 account 和 pickcode**，与 host、其他 query 参数、参数顺序全部无关。

### 4.2 URL 格式

```
{prefix}/api/strm?account={a}&pickcode={p}&file_name={n}&s={sig}
```

不引入 `t` 参数（LitePan 的 `t` 只是共享口令，真正的安全性来自 HMAC；多一个参数多一份维护成本）。

### 4.3 校验

```go
// handler/strm.go 校验段（在 pickcode 格式校验之后）
if signCfg.Enabled {
	sig := q.Get("s")
	want := strm.SignStrmURL(signCfg.Secret, accountName, pickcode)
	if subtle.ConstantTimeCompare([]byte(sig), []byte(want)) != 1 {
		writeJSON(w, http.StatusForbidden, map[string]string{"error": "invalid signature"})
		return
	}
}
```

注意：
- 用 `crypto/subtle.ConstantTimeCompare`，防时序攻击
- **必须先校验 account/pickcode 格式再验签**，避免拿畸形输入做 HMAC
- 签名错误返回 403 而非 404，便于排障

### 4.4 密钥

```go
type StrmSettings struct {
	...
	SignatureEnabled bool   `json:"signatureEnabled"` // 默认 false
	SignatureSecret  string `json:"signatureSecret"`  // 首次开启时自动生成 32 字节随机串
}
```

- 开启时若 secret 为空，自动生成并持久化
- **永不自动轮换**（轮换 = 全部存量 STRM 失效）
- secret 写入 `settings.json`，与 `internalToken` 同等敏感级别

### 4.5 存量 STRM 补签工具

开启签名后，所有旧 STRM 都会 403。必须提供补签：

```go
// handler/strm_sign.go（新增）
// POST /api/strm/sign/backfill
// body: {"targetPaths":["/media/115"], "dryRun":true}
// 行为：递归遍历 .strm → 解析 URL → 重算 s → 原地重写（保留换行符与编码）
```

要点：
- `dryRun` 先出报告（待补签数 / 已合规数 / 解析失败数）
- 只重写 `s` 参数，不动其他 query 顺序
- 幂等：已合规的文件跳过
- 兼容自定义模板（`strmUrlTemplate`）生成的 URL——用 `net/url` 解析后按参数名改，不假设固定格式

## 5. P1-1 扫描改用目录导出（下一轮）

> 状态（2026-10-18）：`ExportDirParse` 已在 P0 清理中**删除**（调用 + 实现，-122 行）；
> 扫描改造的最终方案见 17.5 节的 `cur=0` 全量清单。以下保留为决策记录。

### 5.1 现状比我之前判断的更糟

```go
// task/executor.go:253-261
exportCtx, exportCancel := context.WithTimeout(ctx, 30*time.Second)
defer exportCancel()
if rp, err := deps.Client115.ExportDirParse(exportCtx, itoa(cid), account.Cookie, 0); err != nil {
	warn := "ExportDirParse skipped: " + err.Error()
	...
}
```

不只是"结果没用"，而是**每次任务启动都白白阻塞最多 30 秒**：`ExportDirParse` 内部提交 zip 任务后每秒轮询（`files.go:566-614`），失败才提前返回。等于给每个任务加了最多 30s 的启动延迟 + 一次 115 侧导出任务。

### 5.2 真实情况：现有实现只完成了一半

```go
// files.go:603-607
case 2:
	return statusResp.Data.PickCode, nil   // 只返回导出文件的 pickcode
```

它拿到的是**导出归档文件的 pickcode**，不是目录树。要用起来还缺三步：

```
ExportDirParse → pickcode
  → GetDownloadUrlWebFull(pickcode) → URL
  → 下载导出文件（小，纯文本）
  → 解析行 → (id, pid, name, size, pickcode) → 内存建树 → 路径
```

### 5.3 导出文件格式：必须实测

参考实现 `p115strmhelper/helper/strm/increment.py:294-297` 用的是 `p115client.tool.export_dir.export_dir_parse_iter`，但 **`p115client` 未 vendor 进仓库**（`wheels/` 里没有），无法直接读到字段定义。

**所以第一步是抓一次真实导出文件看格式**，不要凭猜写解析器。

建议实现"格式探测 + 容错解析"：

```go

// 兼容策略：按行 split，自动探测分隔符（\t / , / |），
// 字段数 >= 5 时按 (pickcode, fid, pid, name, size) 位置解析；

func ParseExportTree(r io.Reader) ([]ExportNode, error)
```

### 5.4 路径还原（纯内存，无额外 API）

导出记录自带 `id` 和 `pid`，可以在内存里拓扑建树：

```
nodes → children[pid] → 从 rootCID 开始 DFS 累加路径
```

只要有一条记录的 `pid` 找不到父节点，就判定解析不可信 → 整批回退串行 DFS。

### 5.5 降级矩阵

| 情况 | 行为 |
|---|---|
| 导出提交失败 | 回退串行 DFS，warn |
| 导出超时（10min） | 回退串行 DFS，warn |
| 下载导出文件失败 | 回退串行 DFS，warn |
| 解析行数 < 100 或 pid 断链 | 回退串行 DFS，warn |
| 导出成功 | 用导出结果；**本次禁止清理**（清单可能不全） |

最后一条很关键：学 LitePan 的 `cleanupBlockedReason`——导出模式下拿到的清单如果不完整，删除动作必须禁用。

### 5.6 预期收益

|---|---|---|
| 5 千目录 | ~1.5 小时 | 分钟级 |

## 6. P1-3 代理流 Range 增强（下一轮）

### 6.1 现状

`handler/strm.go:358-472` 的 `handleProxy` 是单流 `io.Copy`，透传 `Range`/`If-Range`，无分片、无刷新。

### 6.2 按收益排序的三件事

**① 链接过期自动刷新（最高优先级）**

```
上游返回 401/403/404/408/429/5xx
  → 重新 ResolveDownloadUrl（带 generation 计数，防并发重复刷新）
  → 最多 2 次
  → 仍失败则断开
```

LitePan 用 `generation` 计数解决"多个分片同时发现过期、同时刷新"的雪崩。

**② 单 Range 分片并发预取**

```
ChunkSize（默认 4MB）+ Concurrency（默认 4）
→ 顺序写回，保证首字节不阻塞
→ 预取窗口 = Concurrency * 2
```

**③ 多 Range multipart**（优先级最低，播放器很少用）

### 6.3 必须接入现有并发限制

分片并发会把 115 侧连接数放大 `Concurrency` 倍。必须接入 `accountProxyConcurrencyLimit`（`strm.go:246-269` 已有 `applyProxyConcurrencyLimit`），否则 `Concurrency=4` × 8 路并发 = 32 连接，容易被风控。

建议：**总连接数上限 = accountProxyConcurrencyLimit**，而不是每路请求各自开 4 个。

## 7. P1-4 EmbyProxy 缓存 TTL

### 7.1 现状

## 14. 实施记录：M3 清理阈值已完成

> 状态：`go build ./...` 通过，`go test ./...` 全绿，`gofmt` 无输出

### 14.1 问题回顾

原实现三处各写一遍「单阈值」判定（`removeExtraFiles`、`cleanupOrphanStrms`、清理页 `executeCleanup`），
默认 `MaxThreshold=10`。一个上万文件的库，网盘移走 11 个文件就整批拒绝，自动清理基本失效；
而单纯把 10 调大，又等于放弃防误删。

### 14.2 改为三重保护

新增 `task/cleanup_policy.go`：

```go
EvaluateCleanup(CleanupInput) (CleanupVerdict, string)
// CleanupAllow / CleanupConfirm / CleanupProtected
```

判定顺序（任一超限即保护）：

| 阈值 | 默认 | 作用 |
|---|---|---|
| `MaxRatio` | 0.10 | 待删 / 本地总数，防「大库小批量」正常删除被误判 |
| `MaxThreshold` | 1000 | 绝对上限，防「小库大批量」误删 |
| `MaxDirs` | 20 | 目录数上限，防分散在多目录的小批量绕过前两者 |
| `StableThreshold` | 5 | 超过则需二次确认（未触发保护时） |

`TotalLocal` / `Dirs` 传 0 表示未知，对应检查自动跳过（清理页场景拿不到本地总数）。

### 14.3 保护态语义

`CleanupProtected` = **只停删除，不停生成**：

- `removeExtraFiles` 返回 `CleanupOutcome{Verdict, Reason}`，任务侧通过 SSE 明确告知原因
- `cleanupOrphanStrms` 输出 warn 日志 + SSE 日志
- 清理页把原因写进 `ThresholdError`，不再是一句笼统的「超过最大阈值」

原实现是静默 `return 0`，用户只看到「任务成功但什么都没删」，无从判断。

## 15. M4（STRM URL 签名）评估结论：不做

> 结论：**从计划中移除**。本节记录依据，避免后续重复提案。

### 15.1 这个功能历史上存在过，且已被主动下线

| 提交 | 版本 | 动作 |
|---|---|---|
| `e939f96` | v1.1.1 | 新增 HMAC-SHA256 签名（T9） |
| `c07b2f5` | v1.1.4 | 加固 secret 生成容错 |
| `86c190c` | **v1.3.8** | **下线整个功能**（-822 行） |

v1.3.8 更新日志原文：

> 移除 STRM URL 签名（HMAC-SHA256）功能：签名 token 有效期仅 24 小时且被硬编码进静态 .strm 文件，
> 生成满 24 小时后整库 STRM 会集体返回 401，**收益远小于风险**。

### 15.2 原实现的致命缺陷（代码实证）

```go
// 旧 internal/service/strm/token.go
const TokenDefaultTTL = 24 * time.Hour

// 旧 buildStrmContent：生成时就把 token 写进文件
url = strm.AppendSignedToken(url, r.TokenSecret, task.Account, f.PickCode, strm.TokenDefaultTTL)
```

- STRM 是**磁盘上的静态文件**，token 写进去后不会再变
- 全仓库**没有任何续签/刷新机制**（`git grep SignStrmToken` 只有生成侧与校验侧两处）
- 结果：开启签名 24 小时后，整库 STRM 全部 401

另外监控侧 `generateStrmContent` **从未接入签名**，开启后监控生成的 STRM 会立即 401。

### 15.3 本轮方案（无过期签名）为什么也不值得做

我原方案去掉了 TTL 陷阱，只签 `account + pickcode`，但收益依然接近于零：

| 想解决的问题 | 实际情况 |
|---|---|
| 防 URL 被扫/被猜 | **pickcode 是 17 位字母数字（≈10^30 组合），本来就不可枚举** |
| 防账号名泄露 | `account` 是用户自定义标签（如「小号」「我的115」），不是 115 登录名 |
| 泄露后可撤销 | 轮换 secret 确实能让旧 URL 失效——**但全量重建 STRM 也能做到，成本相同** |

结论：**签名带来的安全增益 ≈ 0，成本却不低**（签名逻辑 + 批量补签工具 + 兼容开关 + 文档 + 测试）。

### 15.4 如果将来确实要提升安全性，优先级更高的方案

| 方案 | 成本 | 效果 |
|---|---|---|
| `/api/strm` 加 IP 白名单（仅私网/指定网段可访问） | 低 | 直接阻断外网盗链，比签名有效得多 |

## 17.5 M5 方案复核（代码级）：6 处必须修正

> 2026-10-18 第二轮复核：17.4 六步 × 现有代码 × LitePan / p115strmhelper 生产实现。
> 结论：技术路线正确（`cur=0` + pid 还原是两家共同做法），但 17.4 有 2 处会造成**误删 STRM / 路径写错**，必须先改再开工。

### A. 竞品对齐结论（路线不变）

| 维度 | LitePan | p115strmhelper | faststrm 现状 |
|---|---|---|---|
| 清单获取 | `/open/ufile/files` `cur=0`，limit 1150，**空页终止** | `p115client.iter_files(cur=0, with_path=True, with_ancestors=True, cooldown=1.5)` | 逐目录 DFS，1 次调用/目录 |
| 路径还原 | pid→路径缓存 + `/open/folder/get_info` | pid→path 缓存（`ensure_path`） | `folders` 表 cid→path 已在写 |
| 完整性 | count 只做结束校验；空页重试 250ms；重复页中止；缺 ID 中止 | 库内 `raise_for_changed_count` | 无（M5 补） |

即：`cur=0` 无需再验证；M5 的收益点是**调用次数**（页数 vs 目录数），不是"少传数据"。

### B. 六处修正（按严重度）

**①【严重】清理保护写错了维度：清理是 pickcode 维度，不是路径维度**

`cleanupOrphanStrms` 用 `buildCloudPickcodeSet(fileEntries)`（`executor_utils.go:1109`）与本地 STRM 里的 pickcode 比对，跟路径无关。因此：

- 路径翻译失败的条目**只要没进 `fileEntries`，其 pickcode 就不在云端集合里 → 本地已有 STRM 被判孤儿删除**。
- 增量模式只合并本次清单、**不并 DB 快照**（`executor.go:432`），没有任何兜底，最危险；全量模式有 `mergePickcodeSets(snapshot, 本次)`（`executor.go:477`）兜一层。

修正：
- 翻译失败 → **必须**局部 DFS 补齐（补齐的是路径，也是 pickcode 集合）；
- 局部 DFS 也失败的子树 → **本次整任务禁用清理**，不是"覆盖率 <95% 禁清理"。比例阈值挡不住 5% 的精确误删。
- 反向也要防：清理前断言 `len(cloudPickcodes) >= 上次成功清单的 50%`（对齐 LitePan `enhanced.go:233` 的"不足缓存一半跳过"）。

**②【严重】分页终止不能以 `count` 为准**

LitePan 生产代码注释（`full_list.go:44-46`）："分页仍只以连续空页为结束信号，不用 Count 或短页提前结束；Count 仅在结束时用于拦截明确少于声明数量的不完整清单。"

修正：
- 终止条件 = **空页（250ms 重试 1 次仍空）**；
- `count` 只做结束校验：`实得 < count` → 中止并回退 DFS；
- 防死循环：本页 `newIDs == 0` → 中止；条目缺 `fid/file_id` → 中止。

**③【高】`cur=0` 需要独立超时，15s 会直接打回 DFS**

`Client.HTTP.Timeout = 15s`（`qrcode.go:122`）。`cur=0` 首页要服务端递归展开整棵子树，大库极易超 15s；`request115` 重试 3 次仍失败 → M5 整条退化成 DFS。

修正：`RequestOptions` 增加 `Timeout`，`FsFilesAll` 用 60–90s（单独 client 副本，不影响其它调用）。

**④【高】字段别名必须做，且不能改现有 `FsFileEntry`**

现有结构只认短字段（`pc/n/s/fid/cid/pid`，`files.go:345-355`）。`cur=0` 是另一条返回路径，LitePan 对 `fid/file_id`、`fn/file_name`、`pc/pick_code/pickcode`、`size/size_byte/s/fs` 全部做了别名兜底（`models.go:24-53`）。

修正：新增独立 `FullListEntry` + 自定义 `UnmarshalJSON`（**不动 `FsFileEntry`**，它有 10 处调用点）；顺带过滤 `aid=7/120`（回收站，`models.go:198`）。

**⑤【中】pid→路径别造轮子：现成的祖先链接口就在仓库里**

`fsAncestorsViaFiles`（`life.go:783`）已验证：`FsFiles(cid=X, limit=1)` 响应顶层 `path` 就是「根→X」完整链（含自身），与 p115client `update_resp_ancestors` 同源。不需要 `get_info`、不需要抓包。

修正三级回退：
1. `folders` 表命中 **且一致性校验通过**（条目的 `parent_id` 必须等于"父路径那条记录"的 `cid`；不一致=云端改名/移动后缓存陈旧）→ 直接用；
2. 未命中或校验失败 → `FsFiles(pid, limit=1)` 读 `path`，**顺手把链上所有祖先 Upsert 回 `folders` 表**；
3. 仍失败 → 该 pid 局部 DFS。

**⑥【中】`folders` 表会停止维护**

DFS 每目录 Upsert（`executor_utils.go:456`）；M5 没有目录条目，不补的话生活事件的离线路径反查（`GetFolderEntry`）会退化回 API。

修正：解析 pid 时把该目录 + 链上祖先全部 Upsert（与 ⑤-2 合并做）。

### C. 修订版六步（以此为准）

```
1) FsFilesAll(cid=root, cur=0, show_dir=0, fc_mix=1, limit=1000, 超时 60-90s)
   offset 分页；终止=空页(250ms 重试1次)；count 仅结束校验；newIDs==0 / 缺 ID 中止
```

## 19. 修复：含特殊字符的片名无法生成 STRM

### 19.1 根因（代码实证）

同一套「非法字符清理」规则在仓库里存在 **三份实现**，但**写入路径一次都没用上**：

| 位置 | 作用范围 | 是否用于落盘 |
|---|---|---|
| `monitor.sanitizePathParts`（`event_helpers.go`） | 事件生成的部分路径 | 部分使用 |
| `task.sanitizeCloudRelPath`（`executor_utils.go:887`） | **仅** DB 幽灵记录清理时的路径反查 | 否（只用于"查"，不用于"写"） |
| `model.RenderStrmFilenameTemplate` 内联逻辑 | 仅自定义文件名模板 | 仅模板分支 |

全量/增量生成走 `resolveStrmRelPath` → `replaceRelPathExtToStrm`，**目录段与默认文件名都不清理**：

- Windows / SMB：`os.Create` 直接失败（`文件名、目录名或卷标语法不正确`），该文件永远生成不出 STRM；
- 幽灵清理却按清理后的路径去 `os.Stat`，必然查不到 → DB 记录被当幽灵删掉 → 下次增量又重建又失败，形成"反复失败 + DB 记录丢失"。

### 19.2 修复

新增 `pkg/strmutil/sanitize.go`，作为唯一实现（task 与 monitor 共用）：

- `SanitizeFileName(name)`：`:`→`：`、`<>"|?*\`→`_`、控制字符→`_`、去掉段尾空格与点；幂等；`..`→`_` 防路径穿越。
- `SanitizeRelPath(rel)`：按 `/` 逐段清理，返回平台分隔符路径；丢弃 Windows `filepath.Join` 在首段含冒号时引入的伪段 `.`。

接入点（写入、判定、清理三处必须完全一致）：

### 20.2 关键实现决策

- **分页终止只看空页**（250ms 重试一次），`count` 仅在结束时校验 `实得 < count`；另加"重复页"检测（首 FID 与页长都相同 → 中止）防服务端忽略 offset。
- **路径三级回退**：folders 表（带一致性校验）→ `FsFiles(pid, limit=1)` 的顶层 `path`（顺带回填 folders 含祖先链）→ 失败则**整体回退 DFS**。
- **不做部分降级**：任何一个目录翻译失败就整单回退。漏掉的条目 pickcode 不在云端集合里，会被清理逻辑当孤儿删掉。
- **祖先链语义校验**：`path` 末项必须是目标 pid，否则判失败（防"整体错一级"写错目录）；链中间出现空名也判失败。
- **空清单回退**：清单 0 条时返回错误触发 DFS 复核，避免用空集合参与清理。
- 进度：每 5 页推一次"已拉取 N 个文件（匹配 M）"，避免大库长时间 0%。

### 20.3 测试

`task/scan_fulllist_test.go`：空页终止 / count 不完整报错 / 重复页报错 / 请求参数（cur=0 等）/ 字段别名三套 / 祖先链定位 / 缓存一致性（改名后失效）/ 端到端（路径还原 + BDMV 跳过 + 无效 pickcode 跳过）。

### 20.4 预期与观测

| 场景 | 表现 |
|---|---|
| 热启动（folders 表已暖） | 调用次数 ≈ 页数（1 次/1000 文件），比 DFS 少 1 个数量级 |
| 冷启动（folders 空） | 每个含文件目录 1 次祖先链调用，与 DFS 同量级；跑完即转热 |
| 任何异常 | 自动回退 DFS，日志与 SSE 明确告知原因，无需配置开关 |
