## 二、「任务执行」和「STRM 记录」到底是什么（对应问题 2）

### 2.1 现状对照

两个 Tab 背后是**两张完全独立的表**，但它们对「全量任务」记录的是同一件事。

| | 任务执行 | STRM 记录 |
|---|---|---|
| 表 | `task_executions`（`db/task_history_repo.go:16`） | `strm_exec_history`（`db/migrations.go:133`） |
| 一行代表 | **一次任务运行** | **一次 STRM 操作** |
| 谁写入 | 只有 `executor.go:135`（全量/定时任务） | `executor.go:155`（全量任务，kind=`full`）+ `monitor` 的 6 处（kind=`rename`/`move`/`delete`） |
| 生活事件有吗 | ❌ 没有 | ✅ 每个事件一条 |
| 独有字段 | 源路径→目标路径、状态机（running/completed/failed/cancelled）、错误信息 | API 请求数、按 kind 分类 |
| 保留上限 | **无** | 500 条（`db/sqlite.go:73`） |

所以真实语义是：

- **任务执行** = 「我让它跑了一次，跑成什么样」——面向"任务"这个对象。
- **STRM 记录** = 「一次 STRM 生成/改名/移动/删除动作的结果」——面向"动作"。

问题在于**全量任务两边都写了一条**：`task_executions` 一行 + `strm_exec_history` 一行（kind=full）。同一个任务在历史页的两个 Tab 里各出现一次，用户看到的是两份重复信息，只是字段侧重不同。

### 2.2 顺带查出的 6 个问题

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **历史记录的「日志」按钮永远空白** | `TaskHistoryRepo.AddLog`（`task_history_repo.go:157`）**没有任何调用方**；`GetLogs` 查的 `task_logs` 表在本地库里是 **0 行**。`log-detail.tsx:72` 走 `/api/taskHistory/:id/logs` → 返回 `[]` | 点「日志」看到空页面，以为日志丢了。实际日志只在内存（每任务 2 万行，任务结束即丢） |
| 2 | **监控记录的 taskID 全是 `"monitor"`** | `event_handler.go:536` 硬编码 `TaskID: "monitor"`，而函数注释写的是「taskID 用 `monitor:{eventID}` 格式」 | 无法从记录反查是哪个事件；按任务过滤失效 |
| 3 | **监控记录的「文件数」是假的** | `event_handler.go:539` 固定 `TotalFiles: 1`、成功则 `SuccessFiles: 1` | 统计卡「文件成功/总数」把监控事件当文件数累加，数字无意义 |
| 4 | **`increment` 是死枚举** | `StrmHistoryKindIncrement` 无任何写入点（增量已在 v1.4.3 下线），前端 `history.tsx:83` 仍保留「增量任务」标签 | 永远不会出现，但会误导后续维护者 |
| 5 | **任务执行的「删 N」永远是 0** | `executor.go:170` `DeletedFiles: 0, // cleanup 阶段暂未统计` | 「文件」列后面的「（删 N）」从不显示，而清理恰恰是用户最关心的数字 |
| 6 | **`task_logs` 表是死表** | 建表 + 插入函数 + 查询函数齐全，就是没人写 | 白占 schema，让"日志持久化"看起来像做过了 |

### 2.3 命名建议

现在的问题是**名字描述的是"对象"还是"动作"没说清**，而且两者有重叠。

我的建议（按改动成本从低到高）：

**方案 A（只改文案，成本 10 分钟，推荐先做）**

| 现在 | 改为 | 理由 |
|---|---|---|
| 执行历史（页面标题） | **运行记录** | 页面装的不只是"任务"，还有事件 |
| 任务执行 | **任务运行** | 一行 = 一次运行，不是"一个任务"。"任务执行"读起来像任务的定义 |
| STRM 记录 | **事件处理** 或 **STRM 动作** | 它记录的是 rename/move/delete 这些动作；"STRM 记录"太泛，容易和"STRM 生成"混淆 |

**方案 B（消除重复，成本 2 小时）**

- 全量任务不再写 `strm_exec_history`，把 `api_requests` 合并进 `task_executions.summary`。
- Tab 变成「任务运行」+「事件处理」，两个 Tab 各管一类，零重叠。
- 统计卡按 Tab 分别算，不再出现"文件数"混着"事件数"。

**方案 C（大改，不建议）**

合并成一张 `executions` 表，用 `type` 区分。理由：两张表的字段差异（路径/状态 vs api_requests/kind）不小，合并后一半字段恒为空，查询要到处判空，收益不如 B。

我倾向 **A 先做，B 视你对"重复"的容忍度再定**。

## 三、要不要加「运行日记」（对应问题 3）

### 3.1 现在其实已经有了，只是看不到

`handler/strm.go:217` 每次播放请求都会打一行：

```
[STRM] account=xxx pickcode=abcd…xyz decision=redirect reason=default_redirect
       seek=false range_proxy=10MBx2 redirect_check=200 size=4823412224
       method=GET ua="Infuse/7.6" elapsed=12ms
```

`decision` + `reason` 就是"走没走直链"的答案，`reason` 能区分 `explicit_mode_redirect` / `force_proxy_ua:Infuse` / `seek_format_force_proxy` / `redirect_check_failed(403) fallback_proxy` 这些具体原因。

**但**：这行只在文件日志里，而且

- `internal/server/server.go:37-38`：只有 `mode == "prod"` 才写文件，dev 模式只有 stdout；
- 日志级别硬编码 `zapcore.InfoLevel`，没法临时开到 Debug；
- 没有聚合视图——你没法回答"这周有多少次因为 Infuse 走了代理"。

「播放诊断」页能做单次探测，但不留历史。

### 3.2 为什么不能逐条入库

关键数字：**一个播放会话会产生几百次请求**。

- 代理模式下分片默认 10MB（`model/settings.go:164`），一部 4GB 的电影 ≈ **400 次 Range 请求**；
- 每次请求都走 `HandleStrm`，即 400 条日志；
- 一家 4 口每天看 10 部 → 4000 条/天 → 一年 146 万条。

逐条入库 = 一年几百万行，SQLite 会被撑爆，而且这些数据的价值在**分布**，不在**逐条**。

### 3.3 建议：计数全量 + 明细只记异常

**第一层：分钟级聚合（回答"是不是走直链"）**

内存里按 `(分钟, 账号, decision, reason)` 累加计数，每分钟落一条：

```
playback_stats(minute, account, decision, reason, count, bytes, avg_first_byte_ms)
```

- 行数估算：一台设备正常看片，一天有播放的分钟数 ≈ 200 分钟 × 2 个账号 ≈ 400 行/天；保留 7 天 = 2800 行，几十 KB。
- 查询：`SELECT decision, SUM(count) FROM playback_stats WHERE minute > ? GROUP BY decision` → 直连 / 代理占比。
- 表结构用 `(minute, account, decision, reason)` 做唯一键，`INSERT ... ON CONFLICT DO UPDATE count = count + 1`。

**第二层：非默认决策的明细（回答"为什么走了代理"）**

只记录 `reason != default_redirect` 的请求，**内存环形缓冲 200 条**，不落库：

- 内容：时间、账号、pickcode、文件名、decision、reason、UA、耗时。
- 展示在「播放诊断」页底部「最近 10 次非直连」，带"查看日志"跳转。
- 环形缓冲的好处：零磁盘成本，重启即清，本来就是排查用。

**为什么不做「逐条落库 + 清理」**

即便加了保留 7 天的清理，7 天的量也是 2.8 万～28 万行（取决于观看量），写入压力全在播放路径上（每次 Range 都要写一次 DB）。用内存计数 + 分钟落库，写入量从"每请求一次"降到"每分钟一次"，差 3 个数量级。

### 3.4 UI 放哪

不建议新开一个页面。放「播放诊断」页顶部一个区块：

```
最近 24 小时
  直连 1,284 次 (92%)   代理 108 次 (8%)
  代理原因：原盘格式 64 · Infuse UA 31 · 直链预检失败 13
  ─────────────────────────────────
  最近非直连：
   20:31  沙丘2.iso       seek_format_force_proxy    Infuse/7.6
   20:28  奥本海默.mkv     redirect_check_failed(403) Emby/4.8
```

这样"是不是走直链"一眼能看到，出问题再点诊断做单次深度探测。

### 3.5 工作量

| 项 | 内容 | 预估 |
|---|---|---|
| 1 | `playback_stats` 表 + 分钟聚合器（内存 map + 每分钟 flush） | 2h |
| 2 | `HandleStrm` 埋点（决策后一行计数调用） | 30min |
| 3 | 环形缓冲 200 条（只记非默认） | 40min |
| 4 | `GET /api/playbackStats?hours=24` | 40min |
| 5 | 诊断页区块 + 前端类型 | 1.5h |
| 6 | 保留 7 天的清理（挂在每日维护里，见第四节） | 20min |

合计约 **5.5 小时**，可分两次提交（后端一次、前端一次）。

## 四、日志保留与磁盘占用（对应问题 4）

### 4.1 现状：六类数据各自的生命周期

| 数据 | 位置 | 保留策略 | 上限估算 | 评价 |
|---|---|---|---|---|
| 应用日志 `app.log` | `data/logs/` | lumberjack：单文件 50MB、5 个备份、7 天、gzip 压缩（`pkg/logger/logger.go:18-25`） | 原始 ~300MB，压缩后 ~30-60MB | ✅ 已有界 |
| `task_executions` | SQLite | **无** | 每行 ~300B，每天 10 次 → 1.1MB/年 | ⚠️ 只增不减，但量级无害 |
| `task_logs` | SQLite | **无** | 当前 0 行（从未写入） | ⚠️ 死表 |
| `strm_exec_history` | SQLite | 500 条，插入时裁剪（`db/strm_history_repo.go:66-72`） | ~150KB | ✅ 已有界 |
| `.faststrm-trash` 回收站 | 媒体库目录 | 7 天，每小时最多扫一次（`task/executor_utils.go:703-738`） | 取决于删除量 | ✅ 已有界 |
| 任务内存日志 | 进程内存 | 每任务 2 万行，任务结束释放（`task/types.go:265`） | 单任务约 4-8MB | ✅ 已有界 |

**所以：日志不会拖垮运行。** 唯一真正无界的是 `task_executions`，但一年才 1MB 级别。

### 4.2 会不会影响性能

分三种情况：

1. **文件日志**：lumberjack 在达到 50MB 时才滚动一次，平时是顺序追加，开销可忽略。压缩在滚动时做，可能造成一次几百毫秒的停顿，但 50MB 才触发一次。
2. **SQLite 查询**：`task_executions` 有 `created_at` 索引，`ORDER BY created_at DESC LIMIT 50` 走索引，10 万行也不慢。
3. **真正会拖垮的是"逐条写 DB"**：如果按第三节的"逐条入库"方案做，每次 Range 请求都写一次 SQLite，在机械硬盘的 NAS 上会直接拖慢播放起播（每次写要 fsync）。这是我不建议逐条入库的第二个理由。

### 4.3 建议

**必做（成本低、防未来踩坑）**

1. **给 `task_executions` 加保留策略**：保留最近 **200 条**或 **30 天**，取更严的。挂在每日维护里，不新开 goroutine。
2. **`task_logs` 二选一**：
   - 要么**接上**：任务结束时把内存日志里的 `warn/error` 行 + 关键节点（开始/扫描完成/清理完成/结束）批量写入，单次上限 2000 行；
   - 要么**删掉**：连表带 `AddLog`/`GetLogs` 一起删，历史记录的「日志」按钮改成「仅运行中可看」并置灰。
   - 我倾向**接上**，因为"跑完看不到日志"是真实痛点，而"删掉功能"会让排查更依赖 app.log 里的全库日志（多任务并发时混在一起）。

**可选（P3）**

3. `app.log` 的三个参数（大小/备份数/天数）暴露到设置页。多数人不需要，但 NAS 用户会关心。
4. 每日维护时顺便 `PRAGMA incremental_vacuum`，让删掉的行真正释放磁盘页（默认 SQLite 不缩文件）。

**不做**

5. 不建议做"日志导出 zip"：现有 `app.log` 直接拷走就行，加导出功能是给功能加功能。
