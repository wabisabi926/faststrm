## 一、菜单改名：「账号管理」→「网盘账号」

### 现状

侧边栏分组「媒体库」下三个条目：账号管理 / 任务管理 / STRM 清理。

### 结论：建议改，但只改条目名，分组名保留

「账号管理」这个名字的问题不是不好听，而是**指向不明**——账号可以指 Web 登录账号（那是「账号安全」页）、115 网盘账号、Emby 账号。而「网盘账号」一眼就知道是 115。

分组名「媒体库」建议**保留**：组内三项（网盘账号、任务、清理）最终都服务于媒体库，改成分组「115 网盘」反而把 STRM 清理（本地行为）也归到网盘侧，语义更乱。

### 改动点（4 处文案 + 1 处路由注释）

| 文件 | 行 | 现状 | 改为 |
|---|---|---|---|
| `frontend/src/components/app-sidebar.tsx` | 45 | `title: "账号管理"` | `"网盘账号"` |
| `frontend/src/pages/account/index.tsx` | 586 | `<h1>账号管理</h1>` | `网盘账号` |

## 二、概览右上角按钮

### 现状

`home.tsx:272-283`：`刷新` + `管理任务`（跳 `/task`）。

### 方案 A（你提的）：`刷新` + `网盘账号` + `任务管理`

- 优点：两个入口都在，符合"新用户先加账号"的心智
- 缺点：移动端三个按钮会挤成两行；且「任务管理」和侧边栏重复

### 方案 B（推荐）：主按钮随状态变化

```
无网盘账号        → 主按钮「添加网盘账号」  → /account
有账号、无任务    → 主按钮「新建任务」      → /task（可带新建参数）
有账号、有任务    → 主按钮「任务管理」      → /task
```

- `home.tsx` 已有 `accounts` / `tasks` 两个数据源，判断成本为零
- 新用户第一眼看到的就是「添加网盘账号」，不用先去侧边栏找
- 始终只有两个按钮，移动端不挤
- 次按钮仍是「刷新」

**推荐 B**，但如果你更希望入口固定、不做状态变化，就按 A 做（多一个按钮，逻辑更简单）。

### 3.2 问题清单

#### P0 — 死配置误导用户（必修）

**「链接获取 QPS」和「链接获取并发」改了完全无效。**

证据：
- 前端：`BasicSettingsTab.tsx:425-460` 两个输入框可填
- 后端写入：`handler/emby.go:663-667` 只赋值给 settings
- 后端读取：全仓库 0 处（`grep "\.LinkMaxPerSecond\b"` 排除赋值后为 0）

用户以为在调优 115 取链速率，实际没有任何作用。这是设置页里最容易让人困惑的一类问题。

**处理**：
1. 删 UI（整个「下载限流配置」区块，见 P1）
2. 删 `DownloadSettings.LinkMaxPerSecond` / `LinkMaxConcurrent` 字段
3. 删 `handler/emby.go:663-667` 的写入
4. 删前端 `settings/types.ts:83-84` 类型声明
5. 老 settings.json 里残留这两个键无害（JSON 反序列化忽略未知字段）

#### P1 — 冗余合并（建议）

「下载限流配置」和「115 API 限流」本质是同一件事：**控制对 115 的请求压力**。现在拆成两块，且前者 2/3 是死的。

**合并方案**：合成一个区块「115 请求控制」，两组：

```
┌─ 每账号配额（每分钟）───────────────┐
│ 扫描与元数据  [60]   播放取直链 [120] │
│ 生活事件轮询  [60]                    │
├─ 全局兜底 ─────────────────────────┤
│ 全局请求上限（每分钟） [300]          │
├─ 并发 ─────────────────────────────┤
│ 文件下载并发 [2]                      │
└────────────────────────────────────┘
```

收益：少一个区块、少两个无效输入框、概念收口到一处。

#### P2 — 文案与交互（建议）

1. **「重启生效」体验差**：`applyRateLimits` 只在 `server.go:130` 启动时调用一次，保存设置不会重建令牌桶。建议加"保存即生效"：保存设置后调用 `applyRateLimits`（`rate.Registry.Configure` 本身是线程安全的，需确认重建语义）。改完去掉「重启生效」括号。
2. **「常规 API」→「扫描与元数据」**：原文案太笼统，用户不知道包含什么。
3. **「生活事件轮询」加联动说明**：默认轮询间隔 10s ≈ 6 次/分，60 QPM 有 10 倍余量。文案补一句，避免用户以为要按轮询频率调。
4. **布局**：`grid-cols-1 md:grid-cols-4` 在 768-1024px 宽度下四个数字框挤在一起，建议改 `md:grid-cols-2`（2×2）。

#### P3 — 分散配置的可见性（可选）

Cookie 巡检在账号页（`AccountHealthPanel`）、清理策略在 STRM 清理页、Emby/TG 在通知中心。这些分散是**合理的**（各自属于对应业务），但设置中心里没有任何指引。

建议：设置中心底部加一行「其他配置入口」：`清理策略 → /cleanup`　`Emby 通知 → /notify`　`Cookie 巡检 → /account`。

#### P4 — 不建议做的（明确排除）

- **不把 8 个隐藏高级参数暴露到 UI**：与"做减法"相悖，且这些参数 99% 的用户不会碰。保持 settings.json 可改即可。
- **不合并「生活事件监控」页签到基础设置**：监控有独立账号选择、路径映射、状态面板，体量足够独立成页。
- **不改「媒体库」分组名**：见第一节。

## 四、限流区块（截图红框）具体优化

### 4.1 先回答：这个字段是活的

「生活事件轮询（每分钟/账号）」= `rateLimit.lifeQpm`，v1.5.2 已接入：
- `client115/life.go:174` 设置 `DefaultLimiter = rate.TypeLife`
- `client115/life.go:553` 每次请求走 `rate.GetRegistry().Acquire(..., TypeLife)`
- `server.go:389-390` 装配时读取 `LifeQpm`

不是摆设，可以放心调。

### 4.2 它真正的问题：语义孤立

这个字段和另一个页签的「轮询间隔（秒）」是同一件事的两面：

```
轮询间隔 10s  → 实际用量 ≈ 6 次/分/账号
lifeQpm = 60  → 上限 60 次/分/账号（10 倍余量）
```

用户在基础设置里看到 60，不知道它和监控页的 10s 是什么关系，也不知道该不该调。

### 4.3 优化方案（推荐落地）

**布局**
```
grid-cols-1 md:grid-cols-4   →   grid-cols-1 sm:grid-cols-2
```
2×2 排布，中屏不挤。

**分组与文案**

| 现状 | 改为 | 说明文案 |
|---|---|---|
| 常规 API（每分钟/账号） | 扫描与元数据 | 列目录、元数据读取，默认 60 |
| 播放取链（每分钟/账号） | 播放取直链 | 起播与 seek 取链，默认 120 |
| 生活事件轮询（每分钟/账号） | 生活事件轮询 | 与监控页「轮询间隔」联动：10s 间隔约 6 次/分，默认 60 足够 |
| 全局请求上限（每分钟） | 全局兜底上限 | 多账号叠加时的风控保护，默认 300 |

**热生效（可选，见 P2-1）**
改完保存即重建令牌桶，去掉标题里的「重启生效」。

**是否删字段：不删**
四个桶对应四种真实负载（扫描 / 播放 / 监控 / 全局兜底），少任何一个都会回到"互相抢占配额"的老问题。
