# faststrm / p115strmhelper / LitePan 三项目对比与优化方案

> 分析时间：2026-10-18
> 基线版本：faststrm v1.4.2（本地 HEAD `1ec2e69`）
> 对比对象：`D:\Downloads\ai\p115strmhelper`（Python，MoviePilot 插件 v2.8.79）、`D:\Downloads\ai\LitePan`（Go 1.26）
> 本文所有结论均带代码位置，可直接点开核对。

---

## 0. TL;DR

**faststrm 在"播放链路的智能决策"上是三者中最强的，但在"扫描性能模型"和"安全模型"上有两个架构级硬伤。**

| 能力 | faststrm | p115strmhelper | LitePan |
|---|---|---|---|
| STRM 生成性能 | ⚠️ 串行 + 全局 60 QPM | ✅ 128 线程 + Rust | ✅ 115 全量清单 |
| 失效清理安全性 | ⚠️ 阈值 10 个（过小，常失效） | ✅ 10% + CV 稳定性 | ✅ 1000 个 + 保护态 |
| 播放 302 | ✅ 默认 + 预检 | ✅ 唯一模式 | ✅ 可选 |
| 302 前可达性预检 | ✅ 独有 | ❌ | ❌ |
| 内外网智能路由 | ✅ 独有 | ❌ | ❌ |
| 服务端代理流 | ⚠️ 单流 io.Copy | ❌ 无 | ✅ 分片并发 + 刷新 |
| STRM URL 鉴权 | ❌ 无 | ❌ 无 | ✅ token + HMAC |
| 多端同播规避 | ❌ | ✅ same_playback | ❌ |
| Emby 反代 | ✅ 完整 | ❌（只生成外部配置） | ✅ 完整 |
| 多账号 | ✅ | ❌ | ✅ |

**最该先做的三件事：**

1. **拆限流桶**——现在"扫描列目录"和"播放取直链"抢同一个 60 次/分的全局桶，大库扫描时播放会被饿死。
2. **给 STRM URL 加签名**——目前 `/api/strm?account=&pickcode=` 完全裸奔，知道 URL 就能拉流。
3. **修清理阈值**——默认单次最多删 10 个，超过就拒绝，导致自动清理在真实场景基本不工作。

## 1. 三个项目的定位差异

| 项目 | 一句话定位 | 边界 |
|---|---|---|
| **faststrm** | 115 专用「STRM + 智能路由 + Emby 反代」一体化服务 | 不挂载、不转存、不下载媒体本体；深度绑定 115 + Emby 生态 |
| **p115strmhelper** | MoviePilot 插件形态的「STRM 编排器 + 302 签发器 + 风控规避层」 | 依附 MoviePilot 运行，无独立服务；功能最全但无字节流代理 |
| **LitePan** | 多网盘「本地播放网关」 | 11 个驱动、功能面最广，但 115 只有 Open API，无 Cookie 版 |

结论：**faststrm 不需要向 p115strmhelper 的"全功能"靠拢，也不该学 LitePan 的多驱动抽象**。它的差异化价值就在「115 Cookie 直连 + 302/代理智能切换 + Emby 深度适配」，优化应该围绕这条主线加深护城河，而不是横向铺功能。

## 2. STRM 生成对比

### 2.1 URL 格式

| 项目 | 格式 | 鉴权 |
|---|---|---|
| faststrm | `{prefix}/api/strm?account={a}&pickcode={p}&file_name={n}` | **无** |
| p115strmhelper | `{moviepilot}/api/v1/plugin/P115StrmHelper/redirect_url?pickcode={p}` | 无（`allow_anonymous=True`） |
| LitePan | `{base}/api/strm/play/{account}/{b64(fileID)}/t/{token}/n/{name}/s/{HMAC}` | **token + HMAC-SHA256** |

- faststrm：`internal/service/task/executor_utils.go:249-277`（任务）、`internal/service/monitor/event_helpers.go:425-455`（监控）
- LitePan：`internal/strm/url.go:9-26`、`internal/strm/signer.go:10-22`
- 关键细节：**LitePan 的签名只签 path，不含 host**，所以换域名后旧签名仍有效（`baseurl_replace.go` 才能工作）。faststrm 如果要加签名，也应遵循这个原则——因为 EmbyProxy 会往 query 里追加 `redirect=1`（`proxy.go:1329-1343`），如果签整个 query 会直接失效。

### 2.2 遍历与增量

| 维度 | faststrm | p115strmhelper | LitePan |
|---|---|---|---|
| 遍历方式 | 串行显式栈 DFS，每目录 `FsFiles(limit=1000)` 分页 | `iter_files_skim`（SDK 内置并发，cooldown=1.5s） | 串行显式栈 DFS；可选 115 全量清单 |
| 增量依据 | SQLite 快照按 `CloudPath` 比 `PickCode+FileName` | **云端导出目录树 vs 本地 STRM 树差集** | 三种模式：补缺 / 更新（比内容）/ 全量 |
| 云端导出利用 | ❌ 实现了 `ExportDirParse` 但**只用来打日志**（`executor.go:251-266`） | ✅ 增量同步的核心 | ✅ 115 `cur=0&show_dir=0` 一次拉全树 |
| 并发写 | 20 workers（`strmMaxConcurrent`） | 128 解析 + 8 IO writer + 队列 4096 + Rust | finalize 阶段串行 |
| 大库耗时模型 | 目录数 × 1 请求 ÷ 60 QPM | 批处理 5000/批 | 1 次清单请求 + pid→path 补全 |

**这是 faststrm 最大的性能短板。** `listAllFilesRecursive`（`executor_utils.go:304-518`）是纯串行：一个目录一次 API，且和播放共用一个 60 QPM 全局桶。5 万目录的库 ≈ 5 万次请求 ÷ 60/分 ≈ **14 小时**。

而 faststrm 其实**已经有 `ExportDirParse` 的完整实现**（`client115/files.go:514-615`，含提交、每秒轮询、最长 10 分钟），只是调用点只打印了一行 rootPick 日志。这是"代码写了一半没接上"的状态，改造成本极低。

### 2.3 过滤策略

| 策略 | faststrm | p115strmhelper | LitePan |
|---|---|---|---|
| 扩展名 | 任务/全局可配；**监控侧硬编码 `DefaultStrmExtensions`** | 全局 `user_rmt_mediaext` | 任务 → 全局 → 默认 |
| 小文件过滤 | ✅ | ✅ | ✅ |
| 文件名黑名单 | ✅ AC 自动机 | ✅ AC 自动机 | 子串匹配 |
| BDMV/STREAM | ✅ 跳过整棵子树 | ❌ 按扩展名 | ❌ |
| 同名冲突 | ❌ | ❌ | ✅ 按大小/名称选优 |
| 路径长度保护 | ❌ | ❌ | ✅ 单段 >255 字节跳过 |

> faststrm 的监控侧扩展名硬编码是个已知 bug：`event_create.go:44`、`event_rename.go:195`、`phase1.go:566` 全用 `model.DefaultStrmExtensions`，用户自定义扩展名对生活事件无效。`phase1.go:566-568` 的注释自己都写了"Phase 2 会修"，至今未修。

### 2.4 失效清理

| 项目 | 机制 | 阈值 | 问题 |
|---|---|---|---|
| faststrm | 4 套（路径多余 / 增量对账 / 全量预扫 / 独立清理页） | `MaxThreshold=10`、`StableThreshold=5` | **阈值按"个数"而非"比例"，10 个就拒绝** |
| p115strmhelper | 树差集 | 删除比例 >10% 触发 3 次稳定性检查（CV<5%） | 较完善 |
| LitePan | seen 集合比对 + 远端目录比对 | 1000 个 strm 或 20 个目录，超限进入 `Protected` 态，**生成照常、删除全停** | 保护语义清晰 |

faststrm 的清理链路设计其实**比另外两家更完整**（双阈值、二次确认、pending 批次、dry-run、Telegram 按钮、DB 幽灵清理），唯一的问题是**默认阈值定得太小**（`model/settings.go:347-348`）。一个上万文件的库，只要网盘有 11 个文件被移走，自动清理就直接拒绝，用户只能手工去清理页点。

LitePan 的"保护态"语义值得抄：**超阈值时不是整个任务失败，而是"照常生成、只停删除"**，并明确告知原因。

## 3. 播放链路对比

### 3.1 端到端流程

```
【faststrm】
Emby/播放器 → /api/strm?account&pickcode
  → ResolveDownloadUrl（缓存 / 负缓存 / singleflight）
  → DecideRoute（显式 mode > UA 强制代理 > 默认 302）
  → RedirectCheck（HEAD CDN，5s）
     ├─ 可达 → 302 CDN
     └─ 不可达 → 降级 proxy（io.Copy 单流）
  → proxy 超并发 → 反向降级 302

【p115strmhelper】
Emby/播放器 → /redirect_url?pickcode
  → R302Cache (pickcode, UA)
  → Android API + RSA 取链
  → 302 CDN（唯一路径，无代理兜底）

【LitePan】
Emby/播放器 → /api/strm/play/{account}/{key}/t/{token}
  → cache.Coalesce（account+fileID+UA+variant）
  → 驱动 ResolveDownload
  → PickAction：ForceProxy > 账号模式
     ├─ redirect → 302（带 no-store）
     └─ stream  → Range 分片并发代理
```

### 3.2 关键能力矩阵

| 能力 | faststrm | p115strmhelper | LitePan |
|---|---|---|---|
| 302 前可达性预检 | ✅ `RedirectCheck` | ❌ | ❌ |
| 预检结果缓存 | ✅ 4min / 256 条 | — | — |
| 内网/公网智能路由 | ✅ `IsPrivateNetworkIp` | ❌ | ❌ |
| UA 强制代理名单 | ✅ `forceProxyUaTokens` | ❌ | ❌ |
| 直链负缓存 | ✅ 10s | ❌ | ❌ |
| 代理并发降级 | ✅ 超限回落 302 | — | 信号量排队（10s 超时） |
| Range 单请求 | ✅ 透传 | — | ✅ 206 + Content-Range |
| Range 多段 | ❌ | — | ✅ multipart/byteranges |
| 分片并发拉流 | ❌ 单流 io.Copy | — | ✅ 最多 8 并发，按序写 |
| 链接过期自动刷新 | ❌ | ❌ | ✅ generation 去重 |
| HEAD 不请求上游 | ✅ | — | ✅ |
| 多端同播规避 | ❌ | ✅ `same_playback` 复制文件 | ❌ |
| ISO/BDMV 兜底 | ✅ 反代层强制代理 | ❌ | ❌ |

**faststrm 的播放层优势是"决策智能"，劣势是"数据面能力"。** 决策层（预检、内外网、UA、降级）三家最强；数据面（Range 并发、过期刷新）明显弱于 LitePan。

实际影响：代理模式下大文件拖拽进度条时，`io.Copy` 单流会重新建连、无法并发预取，弱网和外网体验差；且 CDN 链接中途过期（115 的 `t` 参数到期）时没有自动换链，只能等客户端重连。

### 3.3 Emby 反代对比

| 能力 | faststrm | p115strmhelper | LitePan |
|---|---|---|---|
| WebSocket | ✅ 裸 TCP 双向转发 + 空闲看门狗 | ❌ | ✅ ReverseProxy FlushInterval=-1 |
| PlaybackInfo 改写 | ✅ 强制 DirectPlay/DirectStream | ❌ | ✅ 同 |
| system/info 端口改写 | ✅ | ❌ | ❌（走通用代理） |
| basehtmlplayer.js 注入 | ✅ 去 crossOrigin | ❌ | ✅ 同 |
| 外部播放器注入 | ✅ PotPlayer/VLC/Infuse/MPV | ❌ | ❌ |
| 多实例 | ❌ 单实例 | ❌ | ✅ 每实例独立端口 |
| 直连客户端白名单 | ❌ | ❌ | ✅ Infuse 直接拿 STRM 文本 |
| 反代端口直接吃 STRM | ❌ | ❌ | ✅ |

faststrm 的反代在三家里是**最贴合 Emby 实际痛点**的（system/info 端口改写 + 外部播放器注入这两项独有），但缺"多实例"和"直连客户端白名单"。

## 4. 302 与 115 API 层对比

### 4.1 取链方式

| 项目 | 主路径 | 备选 | 加密 |
|---|---|---|---|
| faststrm | `POST http://proapi.115.com/android/2.0/ufile/download` | ❌ 无 | 自研 `crypto115`（RSA+XOR） |
| p115strmhelper | 同上（cookie 模式） | ✅ 115 Open API `/open/ufile/downurl` | `p115cipher` |
| LitePan | 115 Open API only | ❌ 无 Cookie 版 | — |

faststrm 和 p115strmhelper 用的是同一套 Android 接口，差异在**风控应对**：

| 风控手段 | faststrm | p115strmhelper |
|---|---|---|
| 405 降级 | 仅错误分类 | ✅ Web API ⇄ App API 自动切换 |
| 端点冷却 | ❌ | ✅ 每端点独立 `ApiEndpointCooldown` |
| Open API 备选 | ❌ | ✅ 1 QPS + 429 `X-RateLimit-Reset` |
| 多端同播 | ❌ | ✅ 复制文件换 pickcode |
| 分享接收码失效重试 | — | ✅ errno 4100008 自动刷新 |

### 4.2 限流：faststrm 的架构级缺陷

**现状（已验证）：**

```go
// internal/service/client115/files.go:90-96
func (c *Client) acquireAPI(ctx context.Context) error {
    lim := rate.GetRegistry().GetLimiter("global", rate.TypeAPI115)  // 硬编码 "global"
    return lim.Acquire(ctx)
}
```

- key 固定为 `"global"`，**所有账号、所有调用共用同一个桶**
- 默认 60 QPM（`rate/registry.go:37`）
- `Registry.SetDefaults` **只有测试调用，生产从不调用**（已 grep 确认）

**致命后果：**

```
扫描列目录 ──┐
播放取直链 ──┼──> 同一个桶 60 次/分
生活事件   ──┘
```

`GetDownloadUrlWebFull` → `request115` → `acquireAPI`（`files.go:254`）。也就是说：**用户在大库全量扫描期间点开一部电影，取直链的请求要和几万次目录请求排队抢令牌。** 表现就是"扫描时播放转圈、偶尔超时"。

p115strmhelper 和 LitePan 都是**账号级独立限流**（p115 还区分接口类型和端点冷却），不存在这个问题。

## 5. faststrm 的 6 个架构级问题（按严重度排序）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | 扫描与播放共用全局 60 QPM 桶 | `client115/files.go:91` | 扫描期间播放卡顿/超时 |

## 6. 优化方案

### P0 —— 架构级，建议立即做

#### P0-1 限流分层（拆桶 + 账号维度）

**问题**：播放取链被扫描饿死。

**方案**（两阶段，可分别上线）：

阶段 1（小改动，先解饿死）：
```
TypeAPI115   -> scan:{account}    60 QPM   扫描列目录
TypePlayback -> play:{account}   120 QPM   取直链（独立桶，扫描不影响）
TypeLife     -> life:{account}    30 QPM   生活事件轮询
+ 全局兜底上限 300 QPM（防多账号叠加触发 115 风控）
```

阶段 2（补账号维度）：`acquireAPI(ctx, account, limiterType)`，`RequestOptions` 增加 `Account` 字段，`GetLimiter` 的 key 从 `"global"` 改为 `{account}:{type}`。

**改动点**：
- `internal/service/rate/registry.go`：新增 `TypePlayback`、`TypeLife`；`SetDefaults` 接入配置
- `internal/service/client115/files.go:90-96`：`acquireAPI` 增加参数
- `internal/service/client115/files.go:218`（取直链）、`life.go`（生活事件）、`executor_utils.go`（扫描）分别传不同 type
- `internal/model/settings.go`：新增 `download.api115Qpm` / `playbackLinkQpm` 等配置项

**风险**：多账号并发时总 QPS 上升 → 必须保留全局兜底上限，且默认值保守。

**验收**：大库全量扫描进行中，播放取链 P99 < 300ms；扫描总耗时不超过原串行基线。

---

#### P0-2 STRM URL 签名（对齐 LitePan，但保留兼容）

**问题**：URL 裸奔。

**方案**：沿用现有 query 风格，追加 `&t={token}&s={sig}`：
```
{sig} = base64url(HMAC-SHA256(secret, account + "|" + pickcode))
```
- **只签 account+pickcode，不签完整 query** —— 因为 EmbyProxy 会追加 `redirect=1`（`proxy.go:1329-1343`），签全 query 会失效
- `signatureEnabled=false` 时行为完全不变（向后兼容，旧 STRM 继续可用）
- 提供"批量补签"工具：扫描现有 STRM，原地重写 URL（对齐 LitePan `token_replace.go`）

**改动点**：
- `internal/model/settings.go`：新增 `strm.signatureEnabled`、`strm.token`
- `executor_utils.go:249-277`、`event_helpers.go:425-455`：URL 生成加签名
- `handler/strm.go:99-239`：校验签名（`subtle.ConstantTimeCompare`）
- `embyproxy/proxy.go`：`isSelfStrmEndpoint` / `resolveRedirectChain` 保持签名参数透传

**风险**：开启后旧 STRM 全部失效 → 必须提供批量补签工具 + 明确提示"需要重新生成或补签"。

**验收**：开启签名后，播放器正常播放；手工去掉 `s` 参数返回 403；旧 STRM 在补签工具执行后恢复。

---

#### P0-3 清理阈值改为"比例 + 绝对值"双阈值

**问题**：默认 10 个，形同虚设。

**方案**（融合 p115 的比例 + LitePan 的绝对值与保护态）：

```
保护触发条件（任一满足即触发）：
  - 本次待删数量 / 本地总数 > 10%
  - 本次待删数量 > 1000
  - 本次待删目录数 > 20

触发后行为（学 LitePan）：
  - 生成/更新照常进行
  - 所有删除动作停止
  - 结果标记 Protected + 原因，推送通知
  - 用户在清理页手动确认后放行
```

**改动点**：`model/settings.go:347-348` 改默认值 + 新增 ratio/abs 字段；`executor_utils.go:684-784`、`825-989`；`handler/strm_cleanup.go:333-418`

**风险**：放宽阈值意味着误删风险上升 → 保留二次确认 + dry-run + pending 批次（这些 faststrm 已经有了，不用重做）。

---

#### P0-4 默认 STRM 前缀修正（快速见效）

**问题**：默认生成 `http://0.0.0.0:8090/api/strm?...`。

**方案**（抄 LitePan `baseurl.go`）：
1. 扫描前检查前缀，`0.0.0.0` / `127.0.0.1` / `localhost` 视为回环，拒绝写入并告警
2. 管理员通过非回环地址访问 Web UI 时，**自动学习当前 host 并持久化为 StrmPrefix**
3. 兜底：读网卡首选内网 IP

**改动点**：`internal/config/config.go`、`executor_utils.go:35-77`（`resolveStrmSettings`）、`server/server.go:111`

**验收**：全新安装不配置前缀时，生成的 STRM 可被同网段 Emby 正常播放。

### P1 —— 性能与体验

#### P1-1 扫描改用 115 目录导出（收益最大）

**现状**：`ExportDirParse` 已实现完整（`files.go:514-615`），但只用来打日志（`executor.go:251-266`）。

**方案**：
1. 用 `ExportDirParse` 一次性拿全量文件清单（含 pid、pickcode、size）
2. pid → 完整路径的翻译，用现有 `folders` 表缓存（`executor_utils.go:410` 已在写）
3. 翻译不完整时**回退到串行 DFS**（兜底，不要硬失败）
4. 清单为空或根路径不匹配时，本次禁止清理（学 LitePan `cleanupBlockedReason`）

**收益**：5 万目录的库从 ~14 小时降到 **分钟级**。
**风险**：115 导出接口有配额/延迟（最长 10 分钟），需要超时回退。

#### P1-2 扫描并发化（P1-1 的兜底）

在账号级限流约束下，目录遍历加 2-4 个 worker + 有界队列，有序合并结果。不要学 p115 的 128 线程——115 风控会直接打脸。

#### P1-3 代理流 Range 增强（抄 LitePan `range_proxy.go`）

按收益排序：
1. **链接过期自动刷新**（最重要）：上游 401/403/404/408/429/5xx 时重新取链，最多 2 次；用 `generation` 计数避免并发重复刷新
2. **单 Range 分片并发**：`ChunkSize` + `Concurrency`（建议 4），预取窗口 + 按序写回，保证首字节不阻塞
3. **多 Range**：`multipart/byteranges`（优先级低，实际播放器很少用）

**改动点**：`handler/strm.go:358-472`（`handleProxy`）
**风险**：分片并发会放大 115 侧的并发压力 → 必须接入 `accountProxyConcurrencyLimit` 信号量。

#### P1-4 EmbyProxy 缓存 TTL 按 CDN 签名收敛

**现状**：`playbackURLCache` 固定 90s（`proxy.go:259-262`），不解析 CDN `t` 参数。
**方案**：`TTL = min(90s, t - now - 60s)`，无 `t` 时 `no-store`。
**收益**：避免"302 拿到已过期链接，客户端 403 且 90s 内不重取"。

#### P1-5 监控侧扩展名修复

`event_create.go:44`、`event_rename.go:195`、`phase1.go:566` 改用 `SettingsStore` 读取用户配置，与任务侧一致。

## 7. 明确不建议抄的部分

| 不建议 | 原因 |
|---|---|
| p115strmhelper 的 FUSE / WebDAV / 分享转存 / 离线下载 / 刮削 | 定位不同，会把"115 + Emby 播放"做成四不像，且每个都是长期维护负担 |
| p115strmhelper 的 128 线程 + Rust 加速 | Go 的 goroutine + 账号级限流更合适；128 并发在 115 风控下反而危险 |
| LitePan 的 11 驱动抽象 | faststrm 只做 115，抽象成本 > 收益，会拖慢迭代 |
| LitePan 的 302 无预检 | **这是 faststrm 的优势，不能丢** |
| LitePan 的 STRM 模板缺失 | faststrm 已有模板能力，应补 UI 保存（现在只能手改文件） |

## 8. 执行顺序建议

```
第 1 批（P0-1 + P0-4）  限流拆分 + 前缀修正      低风险，立竿见影
第 2 批（P0-3）          清理阈值               低风险，纯配置+判定逻辑
第 3 批（P1-1）          扫描改导出             中风险，收益最大
第 4 批（P0-2）          URL 签名               中风险，需配套批量补签工具
第 5 批（P1-3 + P1-4）   代理 Range + TTL       中风险，需要压测
第 6 批（P1-5 + P2-*）   收尾
```

理由：先做"不改变对外行为、纯内部优化"的项（限流、阈值、前缀），再做"改变 STRM 内容格式"的项（签名）——签名一旦上线，所有存量 STRM 都要处理，应该放在批量改写工具之后。
