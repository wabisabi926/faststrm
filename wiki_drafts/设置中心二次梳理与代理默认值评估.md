## 二、覆盖模式：建议移除（这是本轮最值得做的精简）

### 现状

「全局文件过滤」里有「STRM 覆盖模式」两个选项：

| 选项 | 后端行为 | 代码位置 |
|---|---|---|
| 总是覆盖（默认） | 每次都写 | `executor.go:502` |
| 跳过已存在 | **文件存在就跳过，不比较内容** | `executor.go:502-507`、`event_create.go:111` |

### 问题：它和「写盘去重」语义冲突，且会导致内容过期

上一轮加的写盘去重逻辑是：**读旧内容，一致则跳过写入**（`writeStrmFile` 返回 `unchanged`）。这已经实现了「没变就不写」的加速目的。

而 `never` 模式是**只看文件是否存在**，不比内容。两者叠加后的实际效果：

| 场景 | always（默认） | never |
|---|---|---|
| 内容没变 | 跳过写入（去重生效） | 跳过（行为相同） |
| **内容变了**（改了前缀 / 换账号 / pickcode 变化） | 正常重写 ✅ | **仍然跳过 → STRM 里是旧地址 → 全部播放失败** ❌ |

也就是说：`never` 在写盘去重上线后，唯一的额外效果就是**阻止必要的内容更新**。前端文案其实已经提示了这个风险（"源文件改名或换链时可能残留旧链接"），但把它作为可选项留着，等于给用户挖坑。

### 建议

**移除「覆盖模式」选项，固定为 always 行为。**

- 加速需求：已由写盘去重满足（内容相同不写盘、不刷 Emby）
- 字段 `download.overwriteMode` 可以保留（老配置兼容，反序列化忽略），但不再从 UI 暴露、后端不再读
- 风险：确实想"不碰手动改过的 STRM"的用户——但 v1.5.2 已有托管所有权机制（清理时校验指纹），生成侧可以后续同样按指纹判断，而不是靠 never 一刀切

## 三、强制代理默认列表：逐个格式判断

### 当前默认（上一轮已去掉 ts，剩 9 项）

```
iso, bdmv, bdav, dvd, bluray, m2ts, vob, ifo, bup
```

### 判断依据

先明确「为什么需要按格式强制代理」——不是 CDN 不支持 Range，而是：

1. **ISO**：客户端（Emby 网页/官方 APP）**不支持直读 ISO**，需要服务端按 Range 转发，由客户端把它当普通流读（FAQ:194 有明确记录）
2. **原盘目录（BDMV）**：faststrm 已跳过不生成 STRM，但 Emby 可能把 ISO 识别为 `bdmv`/`bluray` 容器
3. **m2ts / ts / vob**：**普通 MPEG-TS / MPEG-PS 视频流文件**，和 mkv 同性质——客户端能直接按 HTTP Range 读，CDN 也支持

### 逐格式结论

| 格式 | 性质 | 是否必须代理 | 判断 |
|---|---|---|---|
| `iso` | 光盘镜像，客户端不能直读 | ✅ 必须 | 保留 |
| `bdmv` | Emby Container 值（蓝光原盘结构） | ✅ 保留 | 防御性，匹配不到无害 |
| `bluray` | 同上 | ✅ 保留 | 同上 |
| `dvd` | 同上 | ✅ 保留 | 同上 |
| `bdav` | 同上（蓝光音视频容器标识） | ✅ 保留 | 同上 |
| `m2ts` | 单个 TS 视频流，几十 GB | ❌ **建议移除** | 与 mkv 同性质，302 直连更省带宽 |
| `ts` | 录播 TS 流 | ❌ 已移除 | 同上 |
| `vob` | DVD 单文件视频流 | ❌ **建议移除** | 同上 |
| `ifo` | DVD 导航文件 | ❌ **建议移除** | **不是视频**，永远不会作为媒体流播放，列入无意义 |
| `bup` | DVD 备份文件 | ❌ **建议移除** | 同上 |

### 支持「m2ts 走 302」的硬证据

1. **本项目历史实践**：v1.3.4 changelog 原文——
   > 「ISO / BDMV / **M2TS** 等原盘格式由「服务器中转」改为「302 直连网盘」：播放器拿到直链后直连网盘拉流，**服务器不参与传输**，流畅看 4K 原盘也不吃 NAS 带宽」

2. **后来回退的原因不是格式问题**：v1.4.0 修复的是
   > 「直链流拦截正则仅匹配 `/videos/{id}/stream`，未兼容 `/emby/` 前缀与 `.mkv` / **`.ts` 等容器后缀**，导致这类请求漏过拦截」

   —— 是反代路径匹配的 bug，不是 m2ts/ts 播不了。

3. **FAQ 的归因**：ISO 播放失败的原因是「Emby 网页端和官方 APP 不支持 ISO 直读（客户端限制）」，m2ts 不存在这个限制。

4. **竞品做法**：LitePan 与 p115strmhelper 都把 m2ts/ts 当普通媒体文件处理，默认 302 直连，没有按格式强制代理的概念。

### 建议的默认列表（5 项）

```go
var DefaultForceProxyFormats = []string{
    "iso", "bdmv", "bdav", "dvd", "bluray",
}
```

**回退方式**：如果某些客户端（或 115 CDN 对特定格式）确实播不了 m2ts，用户在设置页把它加回列表即可——两层会同时生效（上一轮已统一）。

**收益**：一部 40GB 的 m2ts 原盘，从「占 NAS 带宽全量中转」变成「客户端直连 CDN」，对带宽紧张的用户是数量级的改善。

## 四、其他可精简 / 可增加项

### 精简（建议）

| 项 | 建议 | 理由 |
|---|---|---|
| 覆盖模式 | 移除 UI（见第二节） | 与写盘去重冲突，会阻止必要更新 |
| 代理并发上限 / 重定向超时 / 分片参数 | 收进「高级」二级折叠 | 5 个调参项平铺，主界面噪音大；普通用户只需要「按格式代理开关 + 格式列表」 |

### 增加（建议）

| 项 | 内容 | 理由 |
|---|---|---|
| 前缀改动提示 | 前缀输入框下补一句「修改后需重新生成 STRM（重跑任务）才会生效」 | **当前完全没提**，用户改前缀后不重跑，STRM 里还是旧地址，会误判成 bug |
| 默认值提示 | 代理并发上限（8）、重定向超时（5000ms）、分片大小（10MB）/并发（2） | 现有只有部分字段标了默认值 |
| 常用/高级分层 | 路由策略：常用=UA 白名单 + 按格式代理开关 + 列表；高级=并发上限/超时/分片 | 减少主界面认知负担 |

### 明确不建议

- **不暴露**生活事件 8 个隐藏高级参数（去重窗口/重试/整理超时等）——99% 用户不碰，与做减法相悖
- **不做**配置导入/导出——当前配置项不足 40 个，收益低
- **不做**全局「恢复默认值」按钮——误操作风险大于收益（可后续按区块单独加）
- **不动**生活事件监控页签的结构——账号选择/路径映射/状态面板体量足够独立
