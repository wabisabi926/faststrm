## v0.9.5

2026-08-20 · [与 v0.9.4 对比](https://github.com/wabisabi926/faststrm/compare/v0.9.4...v0.9.5)

### 🔥 跨平台本地目录浏览大修（飞牛 fNOS / Docker / Linux / Windows）

针对 v0.9.4 发布后飞牛 fNOS 沙箱下"只能看到 `/vol1/@appshare/faststrm` 一个目录、无法选择媒体文件夹"的 P0 问题彻底修复。

#### P0：飞牛 fNOS 沙箱下根目录列表为空 / 只显示 @appshare

- **根因**：`defaultRoots()` 在 fNOS 环境下依赖 `TRIM_DATA_SHARE_PATHS` 等环境变量，但飞牛只有在 manifest 声明 `share_dirs` 后才会真正 bind mount 并注入这些变量；旧的 manifest 完全没有声明，导致后端拿到的根列表为空或只含 `@appshare` 一项
- **修复**：
  1. **`defaultRoots` 重写为 4 级优先根列表**（从高到低，任一级命中即作为根列表）：
     - `FASTSTRM_LOCAL_DIR_ROOTS` 环境变量（逗号分隔，用户/管理员显式覆盖）
     - Linux：读取 `/proc/mounts` 真实挂载点，过滤 proc/sysfs/devpts/cgroup/overlay/tmpfs 等虚拟 FS（Docker 自定义挂载点从此自动出现在根里，无需硬编码）；Windows 保持盘符枚举不变
     - fNOS 并集：`TRIM_DATA_*` 白名单 ∪ NAS 常见卷根（`/vol1~/vol4`、`/volume1~/volume4`、`/mnt/user|ssd|cache|disk`、`/share|public|home`）
     - 兜底：普通 Linux 硬编码常见目录 + `/`
  2. **`isPathAllowed` fNOS 默认宽松**：之前只要不在白名单就 403，导致 `/vol1/电影` 这类用户已授权、但 manifest 还没声明的路径直接被拒。现在除非显式设置 `FASTSTRM_FNOS_STRICT_PATH=1`，否则一律放行，只打 warning 日志
  3. **新增 `readRealMountpoints()`**：跨平台安全（非 Linux 直接返回 nil），用 FS 类型 + 路径前缀双重过滤虚拟 FS

#### P0：fNOS manifest 缺 share_dirs 声明，沙箱实际无权访问共享目录

- **根因**：旧的 manifest 完全没有 `share_dirs` 字段，飞牛沙箱只把 `@appshare/faststrm` 默认挂载进来，用户在飞牛管理后台勾选共享目录也不会生效
- **修复**：
  1. 在 `FNOS/faststrm-amd64/manifest` 和 `FNOS/faststrm-arm64/manifest` 新增 `share_dirs = /vol1,/volume1,/mnt/user,/mnt/ssd,/mnt/cache,/mnt/disk,/share,/public,/home` 字段，对齐 qmediasync 共享路径声明规范
  2. 用户在飞牛「应用管理 → faststrm → 共享目录」勾选某个共享文件夹并保存后，沙箱里会真正 bind mount 进来，同时写入 `TRIM_DATA_SHARE_PATHS` 供后端枚举

#### P1：前端缺少手动路径输入兜底

- **根因**：本地目录选择器只有树形浏览，根列表不全时用户无法手动输入路径
- **修复**：
  1. `LocalDirectoryTreeDialog.tsx` 顶部新增手动路径输入框（等宽字体 + Enter 提交）+ 「跳转」按钮（带 loading / 禁用态）
  2. 三路校验状态反馈：✅ `ok`（绿色 + 条目数）/ ❌ `err`（红色 + 后端错误原文，含沙箱授权 / 权限 / 路径是否存在提示）/ 💡 idle（用户输入时提示 Enter / 跳转）
  3. 选择树节点会同步回填输入框，方便用户在此基础上微调路径；对话框关闭自动清理状态

## v0.9.4

### 🔥 紧急修复：路径浏览 & 账户状态

针对 v0.9.3 发布后用户反馈的 P0/P1 问题紧急修复：

#### P0：远程路径无法读取

- **根因**：根目录路径处理错误，未直接使用 cid=0；路径格式清理不当；`isDir` 判断逻辑错误（原 `Size == 0 && fc > 0`）
- **修复**：
  1. 根目录直接使用 cid=0，子目录清理路径格式确保以 `/` 开头
  2. 修复 `isDir` 判断为 `fc > 0 && fid == 0`，对齐 115 web API 规范
  3. 前端 `DirectoryTreeDialog.tsx` 改为使用 CID 参数进行 API 调用，避免路径字符串转换失败
  4. 新增 `cid`、`fid`、`path` 字段支持

#### P0：本地路径读取错误（飞牛版本）

- **根因**：fNOS 环境下默认根路径获取不足，未正确探测可用挂载点，缺少路径权限校验
- **修复**：
  1. 优化 `defaultRoots()` 函数，增加 fNOS 环境变量（`TRIM_DATA_ACCESSIBLE_PATHS`、`TRIM_DATA_SHARE_PATHS`）探测
  2. 新增 `isPathAllowed()` 函数校验路径权限
  3. Windows 使用 gopsutil/disk 枚举盘符或回退扫描
  4. 非飞牛 Linux 返回常见挂载点（/mnt、/media、/home 等）

#### P1：账户状态页面缺少状态显示

- **根因**：未调用 `/api/account/status` 接口，缺少状态图标和刷新功能
- **修复**：
  1. 添加状态检查逻辑，调用 API 获取状态
  2. 显示状态图标（正常✓/异常⚠/未知?）
  3. 添加刷新按钮，支持手动检测
  4. 页面加载时自动检测状态

## v0.9.3

2026-08-20 · [与 v0.9.1 对比](https://github.com/wabisabi926/faststrm/compare/v0.9.1...v0.9.3)

### 🔥 紧急修复：fNOS 启动 & 路径浏览 & 任务列表

针对 v0.9.2 发布后用户反馈的 P0/P1 问题紧急修复：

#### P0：飞牛 fNOS 版本无法启动

- **根因**：FNOS/faststrm-{amd64,arm64}/cmd/main 启动脚本缺少 DEFAULT_CONFIG_DIR 环境变量，Go 后端 getDefaultRoot() 找不到默认配置模板
- **影响**：fNOS 环境下应用首次启动时配置初始化失败，应用秒退
- **修复**：添加 `export DEFAULT_CONFIG_DIR="/.config"` 指向打包进 `app/.config/` 的默认模板目录

#### P0：本地路径和网盘路径无法读取

- **根因**：前端使用 POST 发送目录列表请求，但后端路由注册为 GET；响应中 `id` 字段使用数组索引而非完整路径
- **修复**：
  1. 将 `/api/directory/local/list` 路由改为 POST，支持 JSON body 参数 `basePath`
  2. 本地目录列表 `id` 改为完整路径（如 `C:\.Bin`）
  3. 远程目录列表 `id` 优先使用 `cid`/`fid`，兜底用序号，确保唯一性
  4. 优化 fNOS 环境下 `defaultRoots()` 函数，优先返回环境变量目录和常见挂载点

#### P1：任务列表获取失败

- **根因**：`HandleListTasks` 在 `ReadTasks` 失败时直接返回 500 错误，fNOS 环境下可能因权限问题导致 `tasks.json` 无法读取
- **修复**：`ReadTasks` 在文件不存在、权限不足、JSON 解析失败时返回空列表并记录警告日志；`HandleListTasks` 增加 nil 检查和容错处理

#### P1：媒体挂载路径显示"未加载数据"

- **根因**：`HandleMediaMountSyncGET/POST` 在 `ReadSettings` 或 `ReadTasks` 失败时返回 500 错误
- **修复**：`ReadSettings` 返回默认配置而非报错；handler 在读取失败时降级到默认值/空列表继续执行

#### P2：安全加固

- 添加路径穿越防护（`filepath.Clean`、`filepath.IsAbs`、`os.Stat`）

## v0.9.1

`2026-08-20` · [与 v0.8.8 对比](https://github.com/wabisabi926/faststrm/compare/v0.8.8...v0.9.1)

> 本次版本号跳号到 0.9.1，标记 Go 重构完成后的首个稳定发布候选，覆盖 v0.8.8 之后所有 hotfix。

### 🔥 启动与数据兼容性全量修复（响应 v0.8.9.7 审查报告）

针对 [v0.8.9.7 审查报告](https://github.com/wabisabi926/faststrm/blob/v0.8.9.7/faststrm-v0.8.9.7-review.md) 中所有 P0/P1/P2 问题逐条修复。

#### P0：飞牛 FPK 无法启动（二进制路径多一层 `app/`）

- **根因**：`FNOS/faststrm-{amd64,arm64}/cmd/main` 把二进制路径写成 `${TRIM_APPDEST}/app/faststrm`，而飞牛 `TRIM_APPDEST` 已是 `app.tgz` 解压后的 target 根目录，二进制实际位于 `${TRIM_APPDEST}/faststrm`
- **影响**：v0.8.9.7 及之前所有 FPK 安装后启动脚本都找不到二进制，应用秒退
- **修复**：二进制首选路径改为 `${TRIM_APPDEST}/faststrm`，fallback 链保留 `/app/faststrm` 和 `/bin/faststrm`；`upgrade_init`、`uninstall_init` 同步对齐

#### P1a：Shell 脚本 CRLF 导致 Docker 入口脚本执行失败

- **根因**：仓库未配 `.gitattributes`，Windows Git `core.autocrlf=true` 会把 `docker-entrypoint.sh`、`FNOS/**/cmd/*` 检出为 CRLF，Linux 容器执行 CRLF 脚本时出现 `set: Illegal option -` 或 `cannot execute: required file not found`
- **影响**：源码 clone 到 Windows 再本地构建 Docker 时容器启动即退出
- **修复**：
  1. 新建 [.gitattributes](https://github.com/wabisabi926/faststrm/blob/v0.9.1/.gitattributes)：强制 `*.sh`/`FNOS/**/cmd/*`/`Dockerfile`/`*.go`/`*.json`/`*.yml` 等 LF 换行
  2. [Dockerfile](https://github.com/wabisabi926/faststrm/blob/v0.9.1/Dockerfile) 防御性增加 `sed -i 's/\r$//' docker-entrypoint.sh`，即使 `.gitattributes` 未生效也保证 LF

#### P1b：任务文件名不一致导致升级后任务消失

- **根因**：`internal/service/store/tasks.go` 用 `.tasks.json`（dot 前缀），旧版 TS 和 `internal/config/config.go` 初始化逻辑都用 `tasks.json`，导致旧版 `tasks.json` 不被读取、Go 版认为任务文件不存在并自动创建空 `.tasks.json`
- **影响**：从 v0.8.6 及更早版本升级后界面所有任务和定时任务消失
- **修复**：`tasks.go` 文件名改为 `tasks.json`；`config.go` 新增 `migrateDotFile`：启动时检测旧 `.tasks.json` 自动重命名为 `tasks.json`

#### P1c：SQLite 数据库路径迁移缺失导致文件索引数据库变空

- **根因**：TS 版数据库在 `config/filePathDb.sqlite`，Go 版在 `data/filePathDb.sqlite`，迁移代码只有数据库 schema 建表迁移，没有旧文件搬迁逻辑
- **影响**：升级后 STRM 对应的 pickcode 和路径记录丢失，Emby 删除同步无法匹配原有数据库记录，首次重新扫描可能产生重复处理
- **修复**：`config.go` 新增 `migrateSQLite`：检测旧路径 `config/filePathDb.sqlite` 存在而新路径 `data/filePathDb.sqlite` 不存在时，安全重命名主数据库文件及 `-wal`/`-shm` 附属文件

#### P1d：飞牛 amd64 FPK 使用已废弃的架构字段

- **根因**：飞牛新版规范要求用 `platform` 字段（值为 `x86`、`arm`），旧版用 `arch` 字段（值为 `x86_64`、`arm64`）
- **影响**：新版飞牛可能无法识别 FPK 架构
- **修复**：[manifest](https://github.com/wabisabi926/faststrm/blob/v0.9.1/FNOS/faststrm-amd64/manifest) 改为 `platform=x86`（arm64 早已是 `platform=arm`，无需改）

### 🔧 配置语义与生命周期修复

#### P2a：`--config` 参数与 `InitApp` 语义冲突

- **根因**：CLI 把 `--config` 同时当作"用户可写配置目录"和"只读默认模板目录"，导致 `${TRIM_APPDEST}/.config` 下的默认模板完全不被读取，程序只能创建空 JSON
- **修复**：拆分环境变量语义
  - `CONFIG_DIR`：用户可写配置目录
  - `DEFAULT_CONFIG_DIR`：只读默认模板目录（`docker-entrypoint.sh` 默认 `/app/.config`，fNOS 不设置）
  - `DATA_DIR`：业务数据目录
  - `--config` flag：仅代表用户配置目录
- FPK `cmd/main` 移除 `--config` flag 和 `DEFAULT_CONFIG_DIR` 污染，依赖 Go `getDefaultRoot()` 自动解析环境变量

#### P2b：FPK 子进程秒退后仍返回成功

- **根因**：`cmd/main` 在子进程秒退时虽然删除了 PID 文件，但最后仍 `return 0`，导致飞牛面板显示"启动成功"但实际未运行，真正错误只写入 `info.log`
- **修复**：秒退时把 stderr+stdout 写入飞牛面板日志 `TRIM_TEMP_LOGFILE`，并 `return 1` 让面板正确显示"启动失败"

#### P2c：GitHub Release 与 Docker Hub 标签不一致

- **根因**：`v0.8.9.7` 不是标准三段 SemVer，`docker/metadata-action` 的 `semver` 规则不生成对应标签，`docker pull wabisabi926/faststrm:v0.8.9.7` 失败
- **修复**：[release.yml](https://github.com/wabisabi926/faststrm/blob/v0.9.1/.github/workflows/release.yml) Docker metadata 增加 `type=raw,value=${{ github.ref_name }}`，让任意 git tag（包括四段版本号）都能生成同名 Docker Hub tag

### 🐛 飞牛生命周期脚本深度修复（审查新发现）

除报告所列问题外，本次额外审查并修复了 FNOS 回调脚本中未发现的隐患：

#### P0（新）：卸载/升级回调杀不掉 main 启动的进程

- **根因**：`uninstall_init`/`upgrade_init` 用 `pkill -f "^${p} "`（要求 cmdline 以 `${BIN} ` 开头）和 `pkill -xf "${p}"`（要求 cmdline 完全等于 `${BIN}`），但 main 用 `nohup "${BIN}"` 启动，子进程 cmdline 是 `nohup\0/path/faststrm`，两种 pattern 都匹配不到
- **影响**：卸载/升级后 faststrm 仍在跑、端口仍被占用；重装时新进程因端口占用秒退
- **修复**：优先读 `${TRIM_PKGVAR}/app.pid`（main 启动时已写入），用 `kill -TERM` → 5s 等待 → `kill -KILL` 兜底；pkill 改用去掉 `^` 锚定的 `pkill -f "${p}"`，覆盖 fallback 链全部路径

#### P1（新）：main 的 LOG_FILE/PID_FILE 缺少 TRIM_PKGVAR 兜底

- **根因**：`LOG_FILE="${TRIM_PKGVAR}/info.log"` 和 `PID_FILE="${TRIM_PKGVAR}/app.pid"` 在 `TRIM_PKGVAR` 未注入时变成 `/info.log`、`/app.pid`，普通用户无权写根目录
- **影响**：日志全丢、PID 全丢、`stop` 永远找不到进程，进程孤儿化
- **修复**：兜底链 `TRIM_PKGVAR` → `$(dirname $0)/../var` → `/tmp/faststrm-<uid>`

#### P1（新）：install_callback 的可写目录解析与 main 不一致

- **根因**：`install_callback` 的 `__fn_writeable_dir` 只有 3 级 fallback（env → APP_ROOT/xxx → /tmp），而 main 是 4 级（env → `TRIM_PKGVAR/xxx` → `TRIM_APPDEST/xxx` → /tmp），install_callback 把默认 config 放进 `${APP_ROOT}/config`（只读），而 main 启动时优先用 `${TRIM_PKGVAR}/config`（可写），两边解析出的 CONF_DIR 可能不同
- **影响**：install_callback 放的默认模板 main 读不到
- **修复**：install_callback 的 `__fn_writeable_dir` 与 main 完全对齐，fallback 链加入 `${TRIM_PKGVAR}/${fallback}` 一级，并增加 `FNOS_APP_CONFIG_DIR` 等飞牛官方变量识别；同时删除拷贝 `config.yml` 的死代码（Go 后端用纯 JSON，不读 config.yml）

#### P1（新）：uninstall_callback 清理路径与 main 写入路径不匹配

- **根因**：uninstall_callback 只清 `${TRIM_PKGETC:-/app_data/faststrm/config}` 和 `${TRIM_DATA_SHARE_PATHS}/data`，但 main 实际写入的是 `${TRIM_PKGVAR}/{config,data,logs,run}`
- **影响**：用户在 wizard 勾选"删除数据"后，main 写在 `TRIM_PKGVAR` 的数据完全不会被清理，残留并占空间
- **修复**：uninstall_callback 兼容大小写 wizard 变量名（`wizard_delete_data` 或 `WIZARD_DELETE_DATA`），清理路径补充 `${TRIM_PKGVAR}/{config,data,logs,run}`

#### P2（新）：uninstall_init/upgrade_init 用 APP_ROOT 而非 TRIM_APPDEST

- **根因**：`APP_ROOT="$(dirname "${SCRIPT_DIR}")"` 推算根目录，假设 `cmd/` 一定是 `TRIM_APPDEST` 的直接子目录
- **修复**：`APP_ROOT="${TRIM_APPDEST:-$(dirname "${SCRIPT_DIR}")}"`，飞牛未注入时才回退到 dirname

#### P2（新）：main 的 PID_FILE 写入失败未检测

- **根因**：`printf "%s" "${CHILD_PID}" > "${PID_FILE}"` 无任何失败检测，极端情况（磁盘满、目录权限被改）下 printf 失败但脚本继续返回 0，导致下次 `status` 因 PID_FILE 不存在返回 3，再启动一个新进程，造成多实例 + 端口冲突

### ✨ Emby 通知接入

- 新增 `/api/emby/webhook` 接口，可接收 Emby 事件并转发至 Telegram
- 新增「Emby 通知」页面，引导配置 Webhook URL 及事件选择
- 新增 `src/lib/emby/` 模块：client、notifier、types

### 🌐 TG 通知页面全中文

- 轮询状态「Polling is active / not active」→「轮询中 / 轮询未启动」
- 启动轮询、停止轮询、刷新状态等 API 响应消息全部汉化

### 🔧 路由与页面重构

- 原 `/api/telegram/*` 重命名迁移至 `/api/notify/*`
- 原 `/telegram` 页面迁移至 `/notify` 主页面 + `/notify/users` 用户管理页
- 新增 `/tg-notify` 独立的 TG 通知配置页

### 🎨 UI / 布局优化

- 顶部导航栏：SidebarTrigger 移入 header 内部，与其他图标对齐
- STRM 清理卡片：标题与描述间距加大，按钮垂直居中
- 清理卡片状态提示、按钮加载文案统一为中文

### 🔒 安全性

- `.gitignore` 新增 `.config/` 目录，避免本地配置被误提交
- 保留 `config/`、`logs/`、`data/` 等运行时目录忽略规则

### 🚀 STRM 路由策略（方案 B）

- 规则引擎自动决策 + 预检降级
- 302 之前后端先做 `redirectCheck` HEAD 校验
- 两层 LRU 缓存：URL 解析 512 条 / 5min，HEAD 可达性 256 条 / 4min
- 统一日志格式方便排障
