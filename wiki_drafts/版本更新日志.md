## v0.8.6

`2026-08` · [与 v0.8.5 对比](https://github.com/wabisabi926/faststrm/compare/v0.8.5...v0.8.6)

### 🔧 Telegram 轮询自启动优化（核心特性）

新增 `autoPolling` 配置项，实现 Telegram 轮询可控自启动：

- **新增配置**：`settings.json → telegram.autoPolling`，默认 `true`
- **自启动条件**（全部满足时自动启动轮询）：
  1. `autoPolling !== false` — 未被用户显式关闭
  2. `botToken` 已配置
  3. `enabled !== false` — 通知已启用
  4. `webhookUrl` 为空 — 未配置 Webhook
- **运行时自愈**：`pollingTick()` 检测到 `isPollingActive` 为真但定时器已失效时，自动重启轮询（防止进程崩溃/HMR 导致轮询挂起）
- **连接池优化**：新增 `https.Agent` 连接池（`keepAliveMsecs: 30000`），`process.setMaxListeners(30)` 防止 TLSSocket 监听器告警
- **重试逻辑**：`getUpdates` 实现 ECONNRESET/socket hang up 重试，最多 2 次，失败后销毁 agent 重建
- **静默优化**：409 'No new messages' 响应完全静默，网络重试失败降级为 silent/warn 级别

### 📝 TG 通知页面 UI 增强

### 🔒 P0：认证绕过漏洞修复

修复 `/api/strmCleanup/*` 路径未授权访问漏洞：

- **漏洞**：`middleware.ts` 中 `pathname.startsWith("/api/strm")` 误匹配了 `/api/strmCleanup/*`，导致未认证即可执行文件扫描和删除

- **影响**：修复前攻击者可无 token 调用 `/api/strmCleanup/scan` 和 `/api/strmCleanup/execute`

### 🔒 P0：JWT 默认密钥漏洞修复

移除硬编码默认密钥 `your-super-secret-jwt-key-change-in-production`：

- **三级密钥解析**：环境变量 `JWT_SECRET` → 持久化文件 `config/.jwt_secret` → 自动生成 48 字节随机密钥
- **架构改进**：`jwt.ts` 仅依赖 `jose` 库（Edge Runtime 兼容），Node.js 相关操作隔离到 `jwtSecret.ts`
- **启动注入模式**：`layout.tsx` 启动时调用 `setSecret()` 注入密钥到内存，middleware 无需直接访问文件系统
- **生产环境保护**：检测到默认密钥时生产环境拒绝启动，开发环境输出警告

### 🚀 P1：服务自启动

修复重启后定时任务和 Telegram 轮询不自动启动的问题：

- **问题**：`initTaskScheduler()` 仅在访问 `/api/task` 或 `/api/startTask` 时被调用，重启后需手动触发
- **修复**：在 `layout.tsx` 服务端组件中添加启动初始化，包括 JWT 密钥注入、任务调度器初始化、Telegram 轮询自动启动
- **效果**：服务重启后自动恢复所有后台服务，无需人工干预

### 🔧 P1：Telegram Bot 优化

**内部调用改为直接服务层**：

- 消除了 TG Bot 通过 HTTP 调用内部 API 绕过 JWT 认证的问题

**Webhook 安全增强**：

- 新增 `secret_token` 验证（`X-Telegram-Bot-Api-Secret-Token` 头部）
- 支持环境变量 `TELEGRAM_WEBHOOK_SECRET_TOKEN` 和 settings 配置

- **Next.js**：15.4.8 → 15.5.23（修复 Middleware 绕过、DoS、SSRF 等 30+ 漏洞）

## v0.8.3

`2026-08` · [与 v0.8.2 对比](https://github.com/wabisabi926/faststrm/compare/v0.8.2...v0.8.3)

### 🐛 Emby 通知消息格式修复（核心 Bug）

修复所有 Emby 通知消息被二次包装的格式混乱问题：

- **现象**：所有通知被加上 `✅ Task Completed` 前缀和 `Time: ...` 后缀，导致消息格式混乱
- **根因**：`notifier.ts` 调用 `sendTelegramNotification(message, "complete")`，该函数为任务通知设计，会强制添加任务前缀/后缀
- **修复**：
  - 重构通知发送链路，新增 `sendEmbyText`（裸发纯文本）和 `sendEmbyWithPoster`（带海报）
  - 直接调用 `TelegramBot.sendNotification` 发送消息，避免二次包装
  - 入库通知、删除通知、播放通知、删除同步通知全部走裸发链路

### 🖼️ Emby 海报图片发送修复

解决 Emby 内网海报无法被 Telegram 服务器访问的问题：

- **现象**：通知图片发送失败，Telegram 服务器无法访问内网 Emby URL
- **根因**：直接使用 Emby 内网 URL 作为 `photo` 参数，Telegram 服务器需要从公网拉取
- **修复**：
  - 新增 `TelegramBot.sendPhotoFromFile` 方法，先下载海报到本地临时文件
  - 通过 `multipart/form-data` 上传本地文件到 Telegram
  - 失败自动降级纯文本通知（保证消息必达）
  - 修复 `multipart/form-data` 请求头丢失 boundary 的问题（删除手动设置的 `Content-Type`，由 axios 自动处理）

### 🔌 Webhook 路由兼容性修复

- **form-data 兼容**：Emby 默认发送 form-data 格式，原路由仅处理 JSON 导致解析失败
- **现状**：路由同时支持 `application/json` 和 `multipart/form-data`，优先解析 JSON，失败回退解析 form-data 的 `data` 字段

### ⚙️ Webhook runtime 修复

- 声明 `export const runtime = "nodejs"` 和 `export const dynamic = "force-dynamic"`
- 避免 Node 原生模块（fs、os、path）在 edge runtime 中不可用导致的运行时错误

### 🔧 userAgent 字段名修复

- **现象**：Emby 下载海报时 UA 字段错误，使用 `"FastStrm/1.0"` 兜底
- **根因**：配置键名为 `"user-agent"`（带连字符），代码使用 `settings.userAgent`（驼峰），无法正确读取
- **修复**：所有读取处改为 `settings["user-agent"]`

### 🧹 Cookie 过期预警天数移除

- 115 Cookie 不会自动过期（仅人为操作失效），按天数设置预警无意义
- 移除 `expiryWarningDays` 字段：3 个代码文件（serverUtils.ts、alerts/route.ts、tg-notify/page.tsx）和 6 个文档文件
- 保留账号异常/恢复通知功能（由 Cookie 实际状态变化触发，非按天数预警）

### 🗑️ 删除同步通知链路统一

- 修复 `syncDel.ts` 残留的 `sendTelegramNotification` 二次包装 Bug
- 新增 `sendSyncDelText` 函数，与 `notifier.ts` 的 `sendEmbyText` 同语义
- 所有 Emby 相关通知（入库/删除/播放/删除同步）统一走裸发链路

### 📚 Wiki 分类与排序优化

- 使用 `_Sidebar.md` 自定义侧边栏，替代文件名数字前缀方案
- 参考主流项目分类方式：「入门必读 / 核心功能 / 参考资料」三段式结构
- 移除所有 Wiki 页面文件名数字前缀，名称更简洁
